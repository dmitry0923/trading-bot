обвязкой, независимо от того, упоминает ли конкретный артефакт затронутый код:

| WFA/deployment-gate/holdout/MC | все `artifacts/*wfa*`, `*gate*`, `*holdout*`, `*robustness*` | те же + `BacktestRiskSimulator` (№12), funding-veto lookahead (№13) |

для сравнения новых прогонов или как «базу» в новых гипотезах. Они остаются в

## 2. Что НЕ аннулируется

- **Данные:** `candles`, `funding_history`, `cbr_rates_history`,
  `microstructure_snapshots` (forward L1) — это наблюдения, а не результаты стратегий.
- **Инфраструктура:** биржевые спеки, календарь, парсеры, репозитории, security-фиксы,
  сбор микроструктуры (наблюдательный слой).
- **Forward-факты:** например, «в выходные Alor отдаёт последний стакан» — измерение
  источника, не стратегия.
- **Качественные выводы о механике** (например, «WS QuotesSubscribe не работает»)
  остаются, пока не опровергнуты прямым тестом.

## 3. Протокол перезапуска (обязательный)

1. ✅ **Движок исправлен (2026-10-26, `engineVersion 2026-10-26.1`):**
   - entry-bar SL/TP/liq check — `handleProtectiveExits` вызывается сразу после входа;
   - equity-кривая: бар 0 присутствует, последняя метка не дублируется;
   - `BacktestRiskSimulator`: `initialize()` чистит историю, P&L учитывается один раз,

   - пары: beta/z на `i-1`; защитные выходы платят проскальзывание в realistic-режиме.
   Подробности и тесты — `docs/28` §2.1.
2. ✅ **Версия движка зафиксирована:** `BACKTEST_ENGINE_VERSION = "2026-10-26.1"`
   (`backtest/BacktestResult.kt`), попадает в каждый `BacktestResult.engineVersion`.
3. ⏳ **Пересчитать baseline заново** (CNYRUBF 730д, live-риск maxC=1/Kelly) — это

4. ⏳ **Предрегистрировать протокол** нового исследования (docs/26 §11.8 — образец):

5. Публиковать только результаты с `engineVersion` = текущая и пройденными гейтами;
   иначе — `INVALID`/`INCONCLUSIVE`.
6. Любой новый найденный дефект, влияющий на P&L, снова запускает п.1–3 для
   затронутого класса (валидность не «наследуется»).

## 5. Что это меняет в текущей работе

- **Сбор данных не останавливается:** пилот микроструктуры (PID 16080) и
  донакачки candles/funding продолжаются — это вход для нового исследования.
- **Покрытие тестами до 90 %** продолжается: тесты — инструмент обнаружения
  дефектов; каждый новый подтверждённый P&L-дефект добавляется в §3 п.1.
- **Live-параметры не меняются** (maxC=1, Kelly, LIVE-guard CNYRUBF, daily-loss):
  отсутствие валидного edge — не причина включать что-то в LIVE.
- **Никаких выводов «старое всё равно примерно так»**: сравнение с INVALID-числами
  запрещено, пока не пересчитан baseline.

## 7. Финальное решение (после 90 % покрытия)

Финальный список невалидных результатов утверждается **после** завершения работ
по покрытию и правок production-кода. Условия входа в финальное решение:

1. глобальный Kover LINE ≥ 90 % (`test` + `integrationTest`), все проверки зелёные;
2. все подтверждённые P&L-дефекты из docs/28 §2 либо исправлены, либо явно
   признаны «не влияющими на конкретный класс артефактов» с обоснованием;
3. каждому прогону присвоен `engineVersion` (commit + версия движка), старые
   артефакты размечены `INVALID (provisional)`;
4. составлен **impact matrix**: дефект → затронутый код → артефакты, которые его
   использовали.

Процедура финального решения:

1. Для каждого артефакта проверить, проходит ли он через исправленный код
   (entry/exit/P&L/funding/equity). Если да — `INVALID` окончательно.
2. Артефакт может стать `VALID` только если он **пересчитан** на текущем
   `engineVersion` и прошёл свой гейт; «старое число похоже на новое» не основание.
3. Результаты, не зависящие от движка (данные, инфраструктура, security), остаются
   `VALID` без пересчёта.
4. Новый baseline публикуется первым; только после него запускаются новые гипотезы
   по предрегистрированному протоколу.
5. Список и обоснование фиксируются в этом документе (§4) и в `AGENTS.md`;
   решение подтверждается пользователем.

До этого момента: числа не использовать для решений, сравнений и как «базу» —
независимо от того, насколько они выглядят правдоподобно.
