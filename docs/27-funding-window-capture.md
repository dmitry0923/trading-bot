# 27 — P4: Funding-window capture (предрегистрация, research)

> Статус: **research, дефолт off**. Документ фиксируется **до** прогонов. Источник
> задачи — план `18_10_2026.md`, раздел P4 («сбор funding-премии в окнах», +10…25%/год,
> P≈0.25, 0 ₽, 3–4 нед). Здесь описаны правило, модель P&L, контроли и гейт.
> Live-путь (LIVE-guard CNYRUBF, maxC=1, Kelly, `trading.*` флаги) не меняется.

## 1. Гипотеза

Funding у MOEX-perpetual (`SWAPRATE` → руб/контракт/клиринг) — это **плата за перенос**
позиции через клиринг, а не шум: положительная ставка = long платит, short получает
(конвенция зафиксирована в KDoc `FundingVetoGate` и в портфельном движке
`PortfolioMomentumEngine` — `cost += leg.dir * leg.qty * rate`). Гипотеза P4: **доход можно
собирать, выбирая сторону по знаку/величине ставки** — держать ту сторону, которая
*получает* funding, и быть вне рынка, когда ставка мала. Это ортогонально направленному
сигналу: P&L идёт из переноса ставки, не из угадывания цены (в отличие от отброшенного
funding-veto, который был фильтром входа чужого сигнала).

## 3. Модельный дефект, который нужно устранить ДО измерения (обязательное условие)

Проверка кода 2026-10-19 показала, что funding-модель **несогласована между движками**:

| Место | Модель | Направленность |
|---|---|---|
| `PortfolioMomentumEngine.fundingCost` (P1) | `cost += leg.dir * qty * rate` | **направленная** (верно) |
| `BacktestEngine.closePosition` (однотикерный, все WFA) | `pnl = gross − Σ rate × qty` | **нет**: ставка списывается обеим сторонам |
| `PnlCalculator.futures` (LIVE) | `fundingTotal.takeIf { it > 0 } × qty` | **нет + асимметрия**: отрицательный funding (кредит) вообще отбрасывается |

Следствия:
- В однотикерном бэктесте **short с положительной ставкой платит** вместо того, чтобы
  получать → все прежние фьючерсные WFA (730д baseline PF 0.92, combo730, перпетуалы,
  funding-veto/max-hold/ORB) систематически **занижали** short-сторону;
- Гипотеза «сбор funding» в этой модели **неизмерима**: у получающей стороны нет дохода;
- Наоборот, «наивная» реализация без фикса могла бы дать **ложный плюс**: кредит по
  отрицательной ставке начисляется любой стороне, т.е. правило «быть в рынке, когда
  r<0» эксплуатировало бы дефект, а не economics.

**Решение (research-scope):** новый флаг `bt.funding-direction-aware` (**default false** —
reproducibility прежних артефактов) делает P&L направленным по документированной конвенции:
`fundingRub = Σ_d (LONG ? +r_d : −r_d) × qty`. Он используется в прогонах P4, а **тот же
прогон с флагом off — обязательный контроль-фальсификация** (§7). LIVE `PnlCalculator`
не меняется (изменение live-отчётности — отдельное решение пользователя, см. §8).

## 4. Предрегистрированное правило (F1)

- **Ставка решения** `r*`: последнее значение `funding_history` с датой клиринга **строго
  раньше даты бара** (без lookahead; конвенция «решение по вчерашнему клирингу» — часть
  правила, а не деталь реализации).
- **Целевая сторона** на день D:
  - `r* ≥ +thrShort` → **SHORT** (short получает положительный funding);
  - `r* ≤ −thrLong` → **LONG** (long получает отрицательный funding);
  - иначе → **FLAT** (вне рынка).
- **Исполнение**: цель пересчитывается на каждом баре, но меняется только на границе
  торгового дня; переход выполняется по цене **открытия** бара (паритет с остальными
  сигналами: сигнал на закрытии `i−1` → исполнение на открытии `i`). Позиция **удерживается
  через клиринги** — иначе funding не собирается.
- **Стопы**: SL 300 пт / TP 600 пт — **фиксированная** ранее применявшаяся research-сетка
  (не подбирается в этом исследовании); `max-hold` off; liq-симуляция включена (дефолт).
- **Fail-closed**: нет ставки до даты бара (нет истории) → **FLAT** + счётчик
  `bt_funding_window_unknown_total`. На неизвестной ставке позиция **не открывается**
  (никогда не «входим по умолчанию»).
- **Пороги**: первичные `thrLong = thrShort = 2.0 ₽` объявлены **априори**. Сетка
  {0.5, 1, 2, 3, 5} ₽ прогоняется как **проверка плато** (устойчивость к порогу), а не как
  поиск пика; при расхождении «пик ≠ 2.0» вердикт даётся по априорному 2.0.
- **Издержки**: комиссия 1.5 ₽/контракт/сторона (spec), slippage 1 bp, funding — фактические
  `funding_history` по датам клирингов, праздничный календарь MOEX.

## 5. Реализация (выполнена 2026-10-19, **config-only**)

Решение по дизайну: **query-оверрайдов нет** — движок читает `backtestConfig` напрямую,
все пять endpoint'ов (`/backtest` `/validate` `/robustness` `/holdout` `/deployment-gate`)
наследуют `bt.*` автоматически. Калибровка порогов сеткой — перезапуск сервера с
`--bt.funding-window-*` (это дешевле плетения override'ов через `WfaConfig`→`BacktestValidator`/
`FinalHoldoutValidator`→`MonteCarloAnalyzer` и не требует тестов query-контракта на 5 эндпоинтах).

- `BacktestConfig.fundingWindowEnabled/fundingWindowLongThresholdRub/
  fundingWindowShortThresholdRub/fundingWindowBlockOnUnknown/
  fundingWindowRandomSide` (`bt.funding-window-*`,
  env `BT_FUNDING_WINDOW_*`) + `bt.funding-direction-aware`
  (env `BT_FUNDING_DIRECTION_AWARE`), все **default off/false** (воспроизводимость прежних
  артефактов);
- `BacktestEngine.simulate`: расписание цели строится один раз до цикла —
  `fundingWindowDates: TreeMap(fundingHistory)` (`null` при выключенном флаге); на каждом баре
  `fundingWindowTarget(current.time, ...)` → `lowerEntry(barDate)` (строго раньше, без lookahead).
  При включённом окне **детерминированный сигнал и входные фильтры обходятся** (`continue` —
  funding самостоятельный источник решения): FLAT → позиция не трогается, неизвестная ставка →
  fail-closed FLAT (при `blockOnUnknown=true`), смена стороны → закрытие `FUNDING_WINDOW_FLIP`
  + открытие противоположной, выход из окна → `FUNDING_WINDOW_EXIT`;
- направленный funding (`fundingDirectionAware=true`): `fundingChargeSign` в `closePosition` —
  SHORT при положительной ставке **получает** (funding < 0 в P&L), при `false` — прежняя
  direction-agnostic модель (списывает обеим сторонам). Флаг — research-only, LIVE
  `PnlCalculator.futures` не менялся (открытый вопрос §9);
- конструктор `BacktestEngine(..., meterRegistry: MeterRegistry? = null)` — метрики
  `bt_funding_window_unknown_total`, `bt_funding_window_entry_total`,
  `bt_funding_window_exit_total` (тег `ticker`); в тестах подаётся `SimpleMeterRegistry`;
- placebo §7.2 реализован тем же флагом: `fundingWindowRandomSide=true` — «дни в рынке» те же
  (по `|r|` ≥ порога), но сторона = чётность `(ticker.hashCode() + epochDay)` (детерминированно,
  воспроизводимо); при `false` сторона — по знаку ставки;
- SL/TP-проверки остаются **до** P4-блока (приоритет liq/SL/TP выше funding-окна);
- тесты (`BacktestEngineTest`, 8 кейсов): плоские свечи CNYRUBF с фиксированным стартом
  (пн 12.01.2026 — вне новогодних праздников, иначе `MoexHolidayCalendar` даёт 0 клирингов);
  ставка 30.0 → SHORT (direction-aware funding < 0, pnl > 0; legacy — наоборот), −30.0 → LONG,
  1.0 < порога → FLAT, пустой ряд → fail-closed + метрика unknown, HOLD-генератор обходится
  (flag on = 1 сделка / off = 0), смена ставки 30.0→1.0 → `FUNDING_WINDOW_EXIT`,
  смена знака 30.0→−30.0 → `FUNDING_WINDOW_FLIP` (2 сделки), `fundingWindowRandomSide=true`
  при постоянной ставке +30.0: те же дни в рынке, но сторона меняется на границе дня
  (2 сделки-разворот против 1 SHORT в основном режиме) и funding согласован со стороной.

## 6. Прогон по §4 PLAN-001

730д, MINUTE_10, folds=8, live-риск (**maxC=1, Kelly** — не калибровочный профиль),
`fundingDirectionAware=true`, пороги 2.0 ₽. Вердикт — только по holdout/dev-WFA §4:
≥100 OOS-сделок, holdout ≥30 сделок и PF ≥1.30, P(noEdge) < 0.05, CI95 средней сделки ≠ 0,
consistency ≥0.60, robust MC, MDD ≤ 40%.

**Ожидание (до прогона):** число сделок мало (переворот — событие редкое: 157 на 961
клиринг, т.е. ~80 сделок в 730д окне при 2.0 ₽ → **порог 100 OOS-сделок, скорее всего, не
берётся** — тот же ограничитель, что у combo730/перпетуалов, где он не был взят ни разу);
результат, вероятно, `INCONCLUSIVE` по выборке. Это ожидание фиксируется сейчас, чтобы
исход не был подогнан постфактум.

## 7. Обязательные контроли (фальсификация)

1. **`fundingDirectionAware=false`** (прежняя модель) — тот же конфиг. Если результат при
   off **лучше**, чем при on, значит «эдж» создавала асимметрия модели (короткая сторона
   не платит), а не economics → REJECTED независимо от метрик.
2. **Случайная сторона** (аналог placebo): то же расписание окон (те же дни в рынке), но
   сторона выбирается детерминированным псевдослучайным потоком по `(ticker, дата)`
   (**реализовано**: `bt.funding-window-random-side=true`).
   Funding-доход должен схлопнуться (сторона «платящая» половину времени), ценовой P&L —
   остаться шумом. Если случайная сторона даёт не хуже — доход приходил не от funding.
3. **Плато порогов** {0.5…5} — устойчивость, не пик.

## 8. Что НЕ делается

- live-путь не меняется (в т.ч. `PnlCalculator.futures`/`takeIf { it > 0 }`);
- никаких изменений `trading.*`-флагов, LIVE-guard, maxC=1/Kelly;
- чужие тикеры не переносятся в live по результатам P4 (даже при положительном holdout —
  отдельное решение пользователя по протоколу).

## 9. Открытый вопрос (на решение пользователя, следствие §3)

Асимметрия `PnlCalculator.futures` (`takeIf { it > 0 }`: отрицательный funding не
начисляется) означает, что **LIVE-отчётность P&L занижает результат short-позиций** и
делает `AdaptiveRiskService` консервативнее на шортах. Это не research-артефакт, а
расхождение live-модели с конвенцией MOEX; исправление — отдельное решение (влияет на
записанный P&L сделок и на статистику риска).
