# PLAN-001. Достижение 100% годовых на паре CNYRUBF (MOEX). Депозит 50 000 – 100 000 ₽

> Документ отправляется на согласование. Реализовывать план буду я, строго с пошаговой фиксацией всех экспериментов, артефактов, выводов и изменений кода.
>
> **Дата фиксации: 15.10.2026 (15102026).** Фиксируется дорожная карта §5–9 и порядок исполнения (а)→(б)→(в)→(г).

## 1. Цель и жёсткие ограничения

**Цель:** стабильно зарабатывать **≥ 100% годовых** на паре **CNYRUBF** (MOEX), при депозите **50 000 – 100 000 ₽** на старте. Размещение робота — **Yandex Cloud**. Робот должен уметь работать с **несколькими аккаунтами параллельно (10–1000 аккаунтов)** в будущем.

**Критерий успеха (приёмочный, без исключений):**

Стратегия считается годной **ТОЛЬКО** тогда, когда она **одновременно** проходит **весь** блок валидации ниже на полной истории без подбора параметров под holdout.

## 3. Фактическая реализуемость цели «100% годовых»

### 3.1 Математика (депозит 50 000 – 100 000 ₽, CNYRUBF)

Ключевые параметры (production):
- `max-open-positions = 3` (yml), `futures-max-open-positions = 1`, `max-contracts-per-position = 1` (LIVE). Маржа side-specific (GO) — **не статическая** (850–2700 ₽ в зависимости от волатильности), live по живой марже.
- Круговые издержки: **1.5 ₽/контракт/сторона** (broker 1.0 + exchange 0.5) + **slippage ~1.0 bp** + **funding per-clearing** (динамический, SWAPRATE MOEX). Эффективный риск/контракт включает комиссию×2 + slippage×2.
- Ежедневный лосс: `min(2% AUM, 5 000 ₽)` (абсолютный потолок). При 50 000 ₽ — **1 000 ₽/день**.

**Требование к edge (реалистичное):**

Чтобы получать **~100%/год** при **1 контракте**, средний чистый P&L на сделку должен быть **порядка +800–1500 ₽** (в зависимости от частоты сделок 20–40/год) **после всех издержек**. При 2–3 контрактах (если бы лимит позволил, но LIVE maxC=1) — ниже. При **maxC=1 (LIVE)** достижение **100% годовых чистыми** на 50–100k **крайне жёстко** и **невозможно без статистически значимого, воспроизводимого edge на 730д OOS+holdout**.

**Вывод по реализуемости (на текущем стеке/данных):** **Теоретически возможно, но не подтверждено ни одним исследованным кандидатом.** Единственный путь — **найти/построить стратегию, которая стабильно проходит жёсткие статистические гейты (раздел 4), а не оптимизирует IS**.

## 4. Жёсткие критерии приёмки (GATES) — без компромиссов

Ниже — **обязательные гейты**, без прохождения которых стратегия **не идёт в LIVE**. Эти критерии устраняют selection bias и leakage.

| Критерий | Требование (MUST) | Обоснование |
|---|---|---|
| **Горизонт валидации** | **730 дней**, таймфрейм **MINUTE_10**, тикер **CNYRUBF**. | Единственный горизонт, где видно regime-drift (2024→2025→2026). Короткие окна (90–365д) регулярно давали ложноположительные IS-оптимумы. |
| **Walk-Forward** | **Purged/embargoed WFA**, **folds ≥ 8** (предпочтительно 8–10). | Снижает variance OOS-оценки. folds=6 недостаточен для 730д. |
| **Объём OOS** | **≥ 100 OOS-сделок** (строгое требование). | Критический блокер всех кандидатов до сих пор (< 100). |
| **Holdout (out-of-sample вне WFA)** | **Последние 30% истории = holdout, не участвующий ни в одной калибровке**. **≥ 30 сделок в holdout**, **OOS PF_holdout ≥ 1.30**, **Return_holdout ≥ +0%** (не убыточный). | Единственная защита от двойного использования истории. |
| **Статистическая значимость** | **P(noEdge) < 0.05** (two-sided), **CI95 средней сделки не пересекает 0**. | Обязательное условие, а не желательное. |
| **Consistency (walk-forward)** | **≥ 0.60**. | Устойчивость направления OOS по фолдам. |
| **Монте-Карло / робастность** | `robust = true`, **p5 ≥ +0% (минимум)**, **pLoss < 5%**, **stressFailed == 0** (все стресс-сценарии пройдены). | Проверка на чувствительность к шуму/перетасовке. |
| **Deployment-gate** | **`liveAllowed = true`** по **всем** проверкам (`/deployment-gate`) на dev-части (80%) **БЕЗ override**. | Формальный запрет на research-only. |
| **Паритет live↔backtest** | Полный паритет: издержки (×2), funding (per-clearing, по `funding_history`), slippage, liq-симуляция (дефолт on), режимы исполнения, часовые пояса. | Предотвращает optimism bias. |
| **Риск (live-совместимый)** | Проверка на **maxC=1, Kelly/AdaptiveRisk** (НЕ на risk 30%/maxC 100). Калибровочные агрессивные профили использовать **только** для IS-скрининга, **никогда** для финального вердикта LIVE. | Соответствие production-лимитам (раздел 2 AGENTS.md). |
| **MDD и drawdown-дисциплина** | Целевое **Max DD ≤ 40%**, предпочтительно **≤ 30%**. Без экстремальных хвостов DD. | Приемлемо для 50–100k с дисциплиной риск-менеджмента. |
| **Leakage-free** | Любой query-override параметров (funding-veto/ML/session/ORB/time-direction/max-hold/squeeze/panic/macro/VWAP-MR/LLM-veto) **пробрасывается во все пути** (`/validate`, `/backtest`, `/robustness`, `/holdout`, `/deployment-gate`). Проверка автотестами на соответствие. |
| **Репродуцируемость** | Результат воспроизводим (seed MC зафиксирован, семантический кэш LLM обходит при research-WFA, мемоизация по (ticker,barTime,action), `loadHistory=false/true` консистентны). |

> **Правило принятия:** **ВСЕ** пункты выше должны быть **PASS** одновременно. Если хотя бы один FAIL/INCONCLUSIVE — стратегия **отклоняется**.

## 5. Дорожная карта: очередь направлений (а) → (б) → (в) → (г)

**Правила исполнения очереди (жёсткие):**

1. Идём строго по порядку **(а) → (б) → (в) → (г)**. Не переходим к следующему, пока текущее не закрыто.
2. Направление **закрывается** при первом из: **(успех)** проходит **ВСЕ** гейты §4 одновременно — тогда останов и внедрение; **(исчерпание)** данные/инструмент закончились — фиксируется честный `REJECTED`/`INCONCLUSIVE` с артефактом и одной строкой в журнале §9.
3. Любой вывод подтверждается **артефактом** (JSON/CSV прогона + скрипт). Без артефакта шаг не считается выполненным.
4. Внутри направления порядок шагов тоже строгий (a1→a2→…). Пропуск шага запрещён.
5. **Запрещено** гриндить новый грид направленного сигнала на тех же 730д OHLCV (это selection, уже доказано: ORB/time-direction/max-hold/combo730 давали IS-плато и развал на dev-части).

### 5.1 Направление (а) — Execution / издержки на микроструктуре

**Гипотеза.** Детерминированный сигнал на CNYRUBF слаб: **gross** направленного предсказания по OBI растёт лишь до **0.11–0.60 bps** на хвостах, а **круговые издержки = 3–11 bps** (спред 0.75–9.1 bps + комиссия 1.5 ₽/контракт/сторона + slippage ~1 bp). Если снизить стоимость исполнения (пассивная/мейкерская заявка, спред-осознанное размещение, микроценовое таймингование), **чистый** результат может пересечь ноль и, возможно, PF > 1.30. Иначе — платный архив для истории микроструктуры не нужен.

**Текущий статус (факты из кода/прогонов):**

- `microstructure_snapshots` (миграция 037) — forward-L1, пишет `MicrostructureRecorder`; `ticks`/`orderbook_bbo` (миграция 038) — историч. L1 из OrderLog; **все пишутся, но НИЧЕМ не читаются** (read-методы `findByTickerAndTimeBetween` есть, потребителей в `src/main` нет).
- Единственный бесплатный день MOEX OrderLog (2024-10-01, CNYRUBF): **66 328** наблюдений L1 @1 мс + **22 859** сделок; `data/samples/moex_orderlog_20241001`.
- Измерения (`docs/22 §12.1`, `docs/23 §7`): corr(OBI, fwd) 0.09–0.13; хвост |OBI|≥0.9 gross(mid) 0.25–0.60 bps, но **net(taker) −4.29…−4.81 bps**, **net(passive, оптим.) −2.95…−3.63 bps**; momentum-контроль **−0.19…+0.03 bps** (весь gross объясняется импульсом); хвост не кластеризуется (→ «толстая середина»).
- Бэктест-филл (`SimulatedExecution.kt`) — по `open` следующего бара + half-spread / 1 тик; **модели пассивного (maker) филла нет**.
- Live-исполнение: все входы — **лимитные, но маркетабельные по touch** (`AlorClient.placeLimitOrder`, `type="limit"`); **пост-онли/пассивного типа заявки нет**; нет спред-/OBI-осознанного размещения и нет переставления/отмены-догона входа.
- `obiEntryThreshold=0.5` (`TradingConfig.kt:56`) описан в KDoc `MarketDataGate` как блок `OBI_OPPOSING`, но в коде **не применяется**.

**Чего не хватает (конкретно):**

1. **Research read-слой + endpoint** выгрузки `ticks`/`orderbook_bbo`/`microstructure_snapshots` (сейчас read-методы «висят» без потребителя; `ResearchMicrostructureController` фактически отсутствует).
2. **Модель пассивного/maker-филла** в `BacktestEngine`/`SimulatedExecution` (post-only limit, приближение позиции в очереди, частичное исполнение, opportunity-cost при неисполнении) — **это единственный способ проверить гипотезу на 730д**, не имея исторического стакана.
3. **Пост-онли/пассивная заявка** в live-транспорте (`AlorClient`, `RestOrderTransport`, `WsOrderTransport`) + спред-/OBI-осознанное размещение в `ExecutionGateway`/`OrderBuilder` — за флагом `off`, SIM/LIVE-allowlist не трогается.
4. **Свежий `ALOR_REFRESH_TOKEN`** в `.env` + поднятый postgres — для forward-сбора L1 (пилот стоит с 2026-10-02, токен истёк).

**Шаги:**

- **a1.** Реализовать read-слой + endpoint выгрузки микроструктуры (≈1–2 дня).
- **a2.** Реализовать passive-fill модель в бэктесте + query-флаг (`bt.execution-passive-fill-*`, default **off**) на 5 эндпоинтах (`/backtest` `/validate` `/robustness` `/holdout` `/deployment-gate`, паттерн funding-veto) (≈3–4 дня).
- **a3.** Перепрогнать детерминированную базу CNYRUBF **730д, folds=8, live-риск (maxC=1/Kelly)**: сравнить OOS PF/сделки/значимость при taker- vs passive-филле по гейтам §4 (≈0.5 дня прогон).
- **a4.** Реализовать пост-онли заявку + спред/OBI-размещение в live-пути (за флагом off) (≈3–5 дней).
- **a5.** Forward-пилот L1 **≥ 20 торговых дней** (по `docs/23 §4`) на новом исполнении; валидация на 1 бесплатном дне + forward.

**Критерий успеха/остановки:** OOS PF ≥ 1.30 на ≥ 100 сделках при пассивном исполнении **и** P(noEdge) < 0.05, holdout не убыточный. Если на 730д пассив-филл не переворачивает PF 0.92 в ≥1.30 — направление закрывается честным `REJECTED`, платный архив не покупается.

**Структурное ограничение (осознанное):** исторического L1/L2 нет → **WFA на самой микроструктуре невозможен** (только 1 день + forward). Но пассив-филл как **модель исполнения на свечах** проверяем на 730д (пункт a3) — это и есть основной тест. Оценка a5 — вспомогательная (forward — только вперёд).

**Уточнение модели исполнения для корректного A/B (2026-10-17, две правки после ревью a2):**

1. **Maker-филл — точное зеркало taker-филла относительно цены решения.** `executionFill` сначала считает taker-сдвиг (`takerFill`: bps или тик по инструменту), затем `halfSpread = |takerfill.price − reference|` и maker-цена = `reference ∓ halfSpread`. Раньше ветка maker шла **первой** и использовала сток-оценку `(high−low)/4` и для фьючерсов — maker-преимущество завышалось ~3× относительно реального спреда (CNYRUBF: медиана MINUTE_10 range 0.011 ₽ → 0.00275 ₽ против реального спреда 0.80 bps ≈ 0.0005 ₽).
2. **SL/TP выводятся из цены РЕШЕНИЯ (`price`), а не из цены филла.** Это паритет с live: `DecisionEngine` берёт `entryPrice = snapshot.microprice/currentPrice` **на момент решения**, а не фактический филл, и SL/TP считаются от него (`OrderBuilder`). Плюс это обязательное условие валидного A/B: при привязке SL/TP к филлу лучший maker-вход сдвигал бы и стоп/тейк, оставляя R-мультипл неизменным — эффект исполнения исчезал бы. `entryPrice` позиции остаётся фактическим филлом (по нему P&L).

- Дальнейший шаг по очереди §5 — направление **(б)** (донакачка истории/юниверса), которое
  целится непосредственно в блокер «< 100 OOS-сделок» — по решению пользователя.
- **Шаги a4/a5 пропущены по решению пользователя (2026-10-17)**: без подтверждённого edge
  инфраструктура пост-онли-исполнения в live и forward-пилот L1 не имеют предмета проверки
  (a5 к тому же требует свежего `ALOR_REFRESH_TOKEN`, пилот стоит с 2026-10-02). Направление
  **(а) закрыто целиком на шаге a3**; активы в нём — read-слой микроструктуры (a1) и модель
  пассивного филла (a2 + fix), оба остаются в коде под флагами `off` и могут быть
  переиспользованы при возврате к гипотезе исполнения.

### 5.3 Направление (в) — Новый data-слой

**Гипотеза.** Edge требует **признаков, которых сейчас нет** (новости/макро-календарь/ставки/календарные спреды/L2+), а не новых фильтров на OHLCV (последние исчерпаны).

**Текущий статус:**

- **News:** `RgRuNewsProvider` (rg.ru, платная подписка) реализован, конфиг `news.*`, **`enabled=false`**; потребляет только `FundamentalAnalysisAgent` (FX-тикеры пропускают). **Исторического архива новостей нет** (только Redis-кэш TTL 15 мин) → бэктест по новостям невозможен.
- **Macro:** `MacroContextService` — USD/RUB live (ISS), ставка ЦБ и Brent — **из конфига** (`macro.cbr-rate=16.0`); `macro_snapshots` (миграция 023) при `macro.snapshot-enabled=false`. **Макро-календаря нет.**
- **Ставки:** **RUONIA нет**; живого/исторического ряда ставки нет (только статичное поле конфига).
- **Календарные спреды:** near/far + roll-yield **не реализованы**. Есть только FX-pairs (relative-value, REJECTED, OOS PF 0.51) и cross-sectional momentum+carry (граничный, INCONCLUSIVE).
- **L2+ depth:** не хранится (только L1/best, `MicrostructureRestPoller.parse` берёт `bestSide`).
- **Опционы/индекс:** `MoexClient.getFortsOptions` → `ImpliedVolatilityService`; `MoexClient.getVolatilityIndex` → `MarketRegimeService`.

**Чего не хватает:**

1. Исторический архив новостей (платный провайдер либо forward-сбор) — **главный блокер**.
2. Источник + storage макро-календаря (EIA/CPI/заседания ЦБ).
3. Исторический ряд RUONIA/ключевой ставки (источник + storage).
4. Данные near/far контрактов + движок календарного спреда (roll yield).
5. (Опц.) L2+ стакан (Тип А, 90 000 ₽) — только если OBI/depth признаётся перспективным после (а).

**Шаги:**

- **c1.** Подтвердить/подключить источники (rg.ru-подписка статус; ЦБ РФ RUONIA; макро-календарь) (≈3–5 дней).
- **c2.** Storage + фичи + интеграция в агентов/движки (research, default **off**) (≈1–2 нед).
- **c3.** WFA-проверка по §4 (≈1 нед).

**Критерий успеха/остановки:** PF ≥ 1.30, ≥ 100 сделок, P<0.05, holdout>0. Иначе — `REJECTED`.

**Риск:** новостной edge на CNY-инструменте сомнителен (CNY — не новостной); календарные спреды требуют данных контрактов, которых может не быть.

### 5.4 Направление (г) — Смена цели / масштабирование (10–1000 аккаунтов)

**Гипотеза (по фактам):** устойчивый edge ≥ 100%/год на CNYRUBF **не найден** (база 730д OOS −14.8%/PF 0.92; combo730 — RESEARCH_ONLY с holdout −17.6%; риск монотонно ухудшает OOS; все диверсификации/фильтры REJECTED/INCONCLUSIVE; FX-pairs 0.51; portfolio momentum/carry — граничный P 0.04–0.19, критерии не берутся вместе). Значит цель нужно либо **снизить**, либо **монетизировать слабый per-account результат масштабом** (10–1000 аккаунтов).

**Текущий статус multi-account:** каркас есть — реестр `trading_accounts` (021), `TradingAccountService` (weighted round-robin + capacity), per-account AUM/лимиты/daily-loss/locks/outbox/WS-потоки/reconcile/REST API; пустая таблица = legacy single-account.

**Чего не хватает для 10–1000:**

1. Динамическая WS-подписка на новые аккаунты **без рестарта** (сейчас подписка только на старте).
2. Шардирование pipeline / per-account worker pool (сейчас один поток на портфель).
3. Устранение **O(N) запросов на каждый вход** в `selectAccount()` (`COUNT` по каждому кандидату).
4. Масштабирование outbox-worker (сейчас single, глобальный distributed-lock) и reconcile.
5. Горизонтальное масштабирование (Redis/SQL-локи, консистентность in-memory кэшей).

**Шаги:**

- **g1.** Зафиксировать честный вывод: текущие стратегии §4 не проходят (артефакт) — **сразу**.
- **g2.** Решение пользователя: снизить порог доходности (напр. 20–40%/год) **ИЛИ** строить масштабируемую платформу. **Важно: масштаб без edge умножает убыток** — нельзя масштабировать минус.
- **g3.** Если масштаб — динамическая подписка, шардинг, worker pool (≈4–8 нед).

**Критерий:** определяется решением пользователя в g2.

## 8. Риски и допущения

- **Главный риск:** на текущем стеке/данных **устойчивого edge нет** — (а)–(в) могут все закрыться `REJECTED`. Тогда остаётся (г): смена цели.
- **Данные:** историч. L1/L2 отсутствуют (только 1 день); многие инструменты мелкодонные (<3 мес); MOEX ISS ограничен ~2 года.
- **Издержки:** 3–11 bps круговых перекрывают слабый gross; ключ — направление (а).
- **Selection bias:** любой подбор на полной 730д истории обязан проверяться на dev-части (deployment-gate) и holdout.
- **Деньги:** платные архивы (30 000 ₽ Тип B / 90 000 ₽ Тип А) — только по решению пользователя и только после обоснования.
