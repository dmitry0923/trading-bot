## 1. Как правильно читать ошибки

**Для не-айтишника это означает, что:** ошибка — это не ругательство, а подсказка. В ней всегда есть «имя болезни» (тип) и «где болит» (строка, файл, служба). Ошибка выглядит примерно так:

```
java.net.ConnectException: Connection refused: api.alor.ru:443
```

Разбор:
- `java.net.ConnectException` — тип ошибки (дословно «не удалось соединиться»);
- `Connection refused: api.alor.ru:443` — «не пустили по адресу api.alor.ru, порт 443». То есть проблема не в роботе, а в пути до брокера.

Что делать с любой ошибкой: скопируйте **самую последнюю** строку с ключевыми словами (`Error`, `Exception`, `failed`, `refused`, `timeout`) и найдите её в этом документе или в поиске. Не паникуйте из-за всего остального текста.

## 2. Ошибка ConnectionError — робот не может связаться с миром

**Для не-айтишника это означает, что:** робот — как человек, которому не отвечают по телефону. Он звонит брокеру, бирже или нейросети, а ему: «абонент недоступен». Причин обычно три: нет интернета, неверный ключ (дверь не открылась) или нас не пускает «охранник» (файрвол/прокси).

### Шаг 1. Проверьте, что у самого компьютера есть интернет

**Windows (PowerShell):**
```powershell
curl.exe https://api.alor.ru
```
**Linux/ВМ:**
```bash
curl https://api.alor.ru
```
Ожидаемый результат: какой-то текст или код ответа (например, `404`/`403` — это уже значит, что мы **достучались**). Если «Could not resolve host» или «Connection timed out» — нет связи.

Что делать:
- Проверьте Wi-Fi/кабель, перезагрузите роутер;
- Если вы в офисе/университете — спросите, не блокируется ли доступ к биржевым API (бывает у корпоративных файрволов);
- На облачной ВМ (раздел В DEPLOYMENT.md) проверьте, что в настройках ВМ открыт интернет и не включён «останов по балансу».

### Шаг 2. Проверьте ключи — «дверь не открылась»

Если интернет есть, а робот пишет про `Unauthorized` / `401` / `403` / `invalid token` — проблема в пропусках.

- Ключ **истёк** или **перевыпущен** в кабинете брокера → возьмите свежий `ALOR_TOKEN` и `ALOR_REFRESH_TOKEN` (SETUP_GUIDE.md, раздел 3);
- Ключ вставлен **с пробелом** или **не полностью** → в `.env` не должно быть пробелов вокруг `=`, ключ — одна непрерывная строка без кавычек;
- Ключ ИИ (`LLM_API_KEY`) не тот → проверьте в кабинете RouterAI/Kimi/DeepSeek, что ключ активен и на балансе есть средства;
- После правки `.env` не забыли **перезапустить** робота:
  ```powershell
  docker compose up -d --force-recreate
  ```

### Шаг 3. Проверьте «охранников» (файрвол, прокси, антивирус)

- Антивирус/брэндмауэр Windows может блокировать Docker или доступ к `api.alor.ru`/`wss://` — добавьте исключения;
- Если используется прокси — робот должен знать о нём (переменные `HTTP_PROXY`/`HTTPS_PROXY`). В большинстве домашних сетей прокси нет;
- На облачной ВМ проверьте «Группы безопасности» в консоли Yandex Cloud — должен быть разрешён исходящий интернет (по умолчанию разрешён).

### Шаг 4. Проверьте, что робот вообще жив

```powershell
curl.exe http://localhost:8080/actuator/health
```
Если робот не отвечает — сначала почините сам робот (см. таблицу в разделе 5), потом ищите причины ConnectionError в его логах.

## 3. Не хватает памяти (out of memory)

**Для не-айтишника это означает, что:** робот — как холодильник: если его переполнить, он перестанет закрываться. У робота память измеряется в «мегабайтах», и её действительно может не хватить, если компьютер слабый или открыто много программ.

### Симптомы

- В логах: `OutOfMemoryError`, `Killed`, `Cannot allocate memory`, `Container ... is being restarted`;
- Docker показывает ошибки про память, контейнеры постоянно перезапускаются;
- Всё тормозит, страница интерфейса не открывается.

### Лечение (по возрастанию сложности)

1. **Закройте тяжёлые программы** (браузер с сотней вкладок, игры, видеомонтаж) во время работы робота. Обычно этого достаточно.

2. **Снизьте «аппетит» робота** в `.env` — реже просыпаться:
   ```dotenv
   BOT_INTERVAL_MS=600000
   STRATEGY_INTERVAL_MS=1200000
   MONITOR_INTERVAL_MS=60000
   ```
   и перезапустите: `docker compose up -d --force-recreate`. Робот будет думать реже — но и памяти есть меньше.

3. **Отключите тяжёлые сервисы**, которые вам не нужны (например, Grafana и Prometheus, если вы не смотрите графики). Вместо `docker compose up -d` поднимайте только нужное:
   ```powershell
   docker compose up -d postgres redis app
   ```
   (сервисы `prometheus`, `grafana`, `frontend`, `minio` останутся выключенными).

4. **Увеличьте память, выделенную Docker** (Windows):
   - откройте Docker Desktop → шестерёнка (Settings) → **Resources**;
   - увеличьте **Memory** (например, с 2 ГБ до 4–6 ГБ) и нажмите **Apply & Restart**.
   Это разрешит контейнерам пользоваться большей частью вашего «железа».

5. **На облачной ВМ** — «докупите» оперативную память: остановите ВМ в консоли Yandex Cloud, смените конфигурацию (например, 2 vCPU / 4 ГБ → 4 vCPU / 8 ГБ), запустите снова. Более дорого, но надёжно.

6. **Если торгует фьючерс `Si`** — у него тяжёлый риск-движок. Убедитесь, что `MAX_OPEN_POS` невелик (например, `1`).

> **Профилактика:** время от времени освобождайте место в Docker: `docker system prune -f` (удалит неиспользуемые образы и кэш — безопасно).

## 4. Как смотреть логи — чтобы понять, что робот делал ночью

**Для не-айтишника это означает, что:** «логи» — это дневник робота. Он записывает в него каждое заметное действие: открыл позицию, закрыл по стопу, позвал ИИ, получил ошибку. Когда что-то не так — дневник скажет правду.

### Где лежит дневник (логи)

**Если робот запущен через Docker (обычный случай):**
```powershell
# последние 50 записей
docker compose logs app --tail 50

# следить в реальном времени (выход — Ctrl+C)
docker compose logs -f app
```
**Если запущен напрямую через gradlew (разработчики):** вывод идёт в терминал, а при фоновом запуске — в файл `bot.log` в папке проекта:
```powershell
Get-Content bot.log -Tail 50
```
**На облачной ВМ (systemd):**
```bash
journalctl -u trading-bot -f
docker compose logs -f app
```

### Что искать в логах

| Слово в логе | Что случилось |
|---|---|
| `INFO` | обычная запись («открыл позицию SBER») |
| `WARN` / `WARNING` | предупреждение — работает, но обратите внимание |
| `ERROR` | ошибка — что-то не удалось |
| `TRADING_MODE=...` | в какой режиме поднялся робот (первая строка при старте) |
| `STOP_LOSS` / `TAKE_PROFIT` | закрытие позиции по стопу/тейку |
| `daily loss` / `DailyLoss` | сработал дневной лимит убытков (робот встал до следующего дня) |

### Как читать «ночную» жизнь робота

Пример реальной строки и её перевод:
```
2026-08-10 03:15:02 INFO  ... openPosition ticker=SBER qty=10 entry=281.20 ...
```
Перевод: «10 августа в 03:15 по Москве робот открыл позицию по Сберу: 10 акций по цене 281,20 ₽». Сравнивая такие строки с ценой в тот момент, вы понимаете, насколько правильно робот действовал.

> **Если в логах тишина** — это тоже диагноз: робот мог упасть, не запуститься или «уснуть». Проверьте `docker compose ps` (статус контейнера) и `actuator/health`.

## 5. Таблица «симптом → причина → лекарство»

| Симптом (что вы видите) | Причина | Лекарство |
|---|---|---|
| `docker compose` говорит: `DB_PASS is required` / `AUTH_PASSWORD is required` | В `.env` не заполнены обязательные поля | Создайте `.env` (SETUP_GUIDE.md, раздел 4) |
| `JWT_SECRET must be at least 32 bytes` | Слишком короткая секретная подпись | Сгенерируйте строку: `openssl rand -base64 48` |
| `Port 8080 is already in use` | Порт занят другой программой | Найдите виновника: `netstat -ano \| findstr 8080`; закройте его или смените порт |
| Робот не стартует, в логе ошибки Liquibase | База данных ещё не готова при первом старте | Подождите 1–2 минуты, перезапустите: `docker compose up -d` |
| `Connection refused` / `timed out` | Нет интернета / блокировка | См. раздел 2 |
| `Unauthorized` / `401` / `403` | Ключи неверные или протухли | Перевыпустите ключи, обновите `.env`, перезапустите |
| `OutOfMemoryError` / `Killed` | Не хватает памяти | См. раздел 3 |
| В логе: `insufficient candles` при бэктесте | Мало исторических данных | Подождите, пока робот накопит свечи, или увеличьте `days` |
| `totalTrades: 0` в ответе бэктеста | Нет сигналов на таких данных | Норма: мало данных или слабые сигналы; попробуйте другой тикер |
| В логе `TRADING_MODE=LIVE` при первом запуске | Случайно включён реальный режим | Немедленно поставьте `SIMULATION` и перезапустите |
| Контейнеры `restarting` бесконечно | Падает приложение (обычно ключ/БД) | `docker compose logs app` → смотрите последнюю ошибку |
| Веб-интерфейс открывается, но логин не принимает | Неверные `AUTH_USER`/`AUTH_PASSWORD` или не перезапускали после правки | Проверьте `.env` и перезапустите |
| Робот «молчит» после полуночи | Дневной лимит убытков сработал, или вне торговых часов | Проверьте `trading-hours-*` и `max-daily-loss-rub` |

## 6. Частые вопросы

### «Робот потерял деньги за ночь, что делать?»
Сначала без паники. Посмотрите логи (раздел 4): если там `STOP_LOSS` — робот честно срезал убыток по правилам. Если там ошибки соединения в момент падения рынка — значит, робот не смог закрыться вовремя; это повод разобраться с интернетом/ВМ (раздел 2). И помните: убытки — нормальная часть торговли, задача робота — чтобы они были маленькими и контролируемыми.

### «Можно ли удалить виртуальные позиции из песочницы?»
Можно остановить робота, очистить таблицу в базе и запустить заново. Но для новичка это необязательно: виртуальные позиции ни на что не влияют, кроме статистики. Если решите чистить — сделайте бэкап: `docker compose exec postgres pg_dump -U trader trading_bot > backup.sql`.

### «Что значит DOWN в ответе health?»
Робот считает себя больным: не достучался до базы данных, Redis или брокера. Смотрите логи (`docker compose logs app`) — там будет конкретная причина (обычно раздел 2 или «база не поднялась»). Затем `docker compose up -d --force-recreate`.

### «Как понять, что робот обновился до новой версии?»
В логах при старте ищите строку приветствия с версией, или сравните `docker compose ps` (дата создания контейнера). После `git pull` всегда делайте `docker compose up -d --build`, иначе робот продолжит работать на старой версии.

### «Робот не торгует по понедельникам, это баг?»
Проверьте `trading-hours-start: "10:00"` и `trading-hours-end: "18:30"` — это окно московского времени, когда биржа открыта. Вне него робот по задумке «спит». Это не баг, а защита от торговли в нерабочее время.

### «Стоит ли запускать робота на домашнем компьютере в LIVE?»
Только если компьютер гарантированно не уснёт и не перезагрузится (выключите спящий режим и автообновление — раздел Б DEPLOYMENT.md). Для серьёзной торговли надёжнее облачная ВМ (раздел В). Ваш домашний ПК не имеет резервного питания и стабильного канала, а биржа ошибок не прощает.
