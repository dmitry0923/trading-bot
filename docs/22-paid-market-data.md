### 1.2 Тип А vs Тип В: что реально нужно проекту

| Тип | Содержимое | Формат | Что позволяет считать |
|---|---|---|---|
| **Тип А — Order Log** | все сделки + все заявки (полный L3) | csv, срочный рынок с 2016-01 | всё: OBI, microprice, **VPIN**, глубина, slope-of-book, queue position |
| **Тип В — Top of Book** | все сделки + лучшие заявки | csv, срочный рынок с 2016-01 | OBI, microprice, TBBO, спред, **но не depth-признаки** |
| **Тип С — Deals** | только сделки | csv/xml, с 2000-11 | тик-лента, VWAP, tape-reading |

Ключевое: **весь текущий слой микроструктуры (`obi`, `microprice`, `spread_bps`,
`microprice_deviation_bps`) считается по BBO → Тип В закрывает его полностью.**
Тип А нужен только если захотим VPIN/глубину позже. Поэтому 30 000 ₽ вместо 90 000 ₽.

Объём **измерен фактически** — см. раздел 1.3: бесплатный образец скачан и разобран.

### 1.3 Бесплатные образцы: что скачано и измерено (2026-10-01)

Образцы на странице **бесплатны и лежат в публичном каталоге с листингом**
`https://ftp.moex.com/pub/info/data/` → `Derivatives Market/`. Проверено: в каталоге
**только один день (2024-10-01)** — то есть архив за прошлые даты действительно платный
(`OrderLog20240901_B.7z` → 404). Само дерево каталогов открыто.

| Файл | Размер | Что это |
|---|---|---|
| `.../Derivatives Market/OrderLog20241001_B.7z` | 97,2 МБ | Тип В, **срочный рынок**, 1 день |
| `.../Derivatives Market/OrderLog20241001_A.7z` | 436,6 МБ | Тип А, срочный рынок, 1 день |

Скачан и разобран Тип В. Внутри — 4 вложенных 7z: `fut_deal`, `fut_tick`, `opt_deal`,
`opt_tick`. Нам нужны только `*_fut_*` (опционы не берём).

**Формат (фактически, не по описанию в a1681):**

`YYYYMMDD_fut_tick.csv` — стаканы, 615,3 МБ на день на весь рынок (14 629 290 строк):

```
#SYMBOL,SYSTEM,TYPE,MOMENT,DEAL_ID,PRICE,VOLUME
CNYRUBF,F,B,20240930185802963,,11.11100,50
CNYRUBF,F,S,20241001184958607,,13.28200,3
```

- `TYPE`: `B` = bid, `S` = ask/offer;
- `MOMENT` = 17 цифр `yyyyMMddHHmmssSSS` (миллисекунды);
- `DEAL_ID` пуст для котировок, заполнен, если заявка сматчилась;
- `SYSTEM` = `F` (фьючерсы).

`YYYYMMDD_fut_deal.csv` — сделки, 78,3 МБ на день:

```
#SYMBOL,SYSTEM,MOMENT,ID_DEAL,PRICE_DEAL,VOLUME,OPEN_POS,DIRECTION
CNYRUBF,F,20240930190505117,2024117270837460993,13.22400,5,8128542,B
```

**Правило реконструкции BBO (это и есть то, что нужно для OBI/microprice):**
для каждого `MOMENT` → `best_bid = max(PRICE) среди TYPE=B`, `best_ask = min(PRICE) среди TYPE=S`.
Моменты часто содержат **только одну сторону** (например, последний момент файла —
три строки только `S`), поэтому **противоположную сторону нужно carry forward** с
предыдущего момента — ровно как в live-`MarketDataGate`.

**Замеры по CNYRUBF за 2024-10-01 (1 день, весь фьючерсный рынок = 357 инструментов):**

| Величина | Значение |
|---|---|
| Доля CNYRUBF в `fut_tick.csv` рынка | **1,48 %** (216 653 из 14 629 290 строк) |
| Объём CSV по CNYRUBF | **9,6 МБ/день** (средняя строка 46,7 байта) |
| **Прогноз на 512 торговых дней** | **≈ 5,0 ГБ CSV** (без сжатия) — диск не проблема |
| Строк-котировок | 216 653 (B 109 884 / S 106 769) |
| Уникальных моментов | 68 300 (в среднем 3,2 строки на момент) |
| Глубина | 1 уровень — 35 171 момент, 2 — 12 570, хвост до 275 на открытии сессии |
| Сделок CNYRUBF | **22 859/день** → ≈ 11,7 млн за 2 года |
| Спред | bid 11,111–13,808 / ask 12,637–13,329; трейды 13,099–13,328 |

**Профиль сессии CNYRUBF (объём сделок по часам МСК) — существенно для калибровки
session/time-direction фильтров:**

| Час | Сделок | Объём |
|---|---|---|
| 09:00 | 4 | 50 |
| **10:00** | **5 984** | **262 951** |
| **11:00** | **4 233** | **182 839** |
| 12:00 | 905 | 59 256 |
| 13:00 | 1 822 | 104 533 |
| 14:00 | 695 | 54 105 |
| 15:00 | 3 031 | 125 314 |
| 16:00 | 2 266 | 257 684 |
| 17:00 | 1 683 | 111 506 |
| 18:00 | 1 537 | 60 768 |
| 19:00–23:00 | 699 суммарно | **26 266** |

Вывод: CNYRUBF — **дневной инструмент с пиком 10:00–11:00 МСК**; вечерняя сессия
(19:00–23:00) даёт ~2 % объёма. Это согласуется с тем, что в калибровке 2026-09-24
лучшим одиночным фильтром был «блок LONG до 09:00», а «session 14:00–18:00» ухудшал
результат. Данных за один день для вывода мало, но при разборе 2 лет это нужно
перепроверить на полной выборке.

**Дефект данных (обязательно учесть в парсере):** самый первый момент файла
(`20240930185802963`, первые ~20 мс вечерней сессии) содержит 25-уровневую лестницу
bids с ценами **11,111…12,995** при ask 13,31–13,325 — спред ~12 %, это слежавшиеся
остатки предыдущего ценового режима. Через 4 мс (`...967`) bids уже 13,00–13,14 и к
`...983` сходятся с ask. **Ровно 1 момент из 68 300** (0,0015 % сделок), т.е. это
артефакт открытия сессии. Парсер должен отбрасывать первые N мс каждой сессии
(или брать последнее корректное состояние), иначе в OBI попадёт спред 12 %.

**Прочие особенности формата:**

- имя файла = **торговый день**, а `MOMENT` начинается с **18:50 предыдущего календарного
  дня** (вечерняя сессия). Нельзя фильтровать по дате `MOMENT` — фильтровать по дате
  из имени файла, иначе потеряется вечерняя сессия;
- CNYRUBF в файле — **вечный** контракт (без кодов месяцев, в отличие от `SiH5`,
  `SiH6`, `BRV4` и др.) — код инструмента стабилен, joins не нужны;
- данные обезличенные (контрагенты удалены) — ограничений по персональным данным нет;
- кодировка — ASCII/CP1251, разделитель `,`, заголовок начинается с `#`.



Формат файлов и раскладка полей документированы: <https://www.moex.com/a1681>
(типы A/B для срочного рынка, есть примеры записей). Специальный SDK не нужен —
парсер пишется на фиксированную ширину / CSV.

### Тип A vs Тип B (важно для выбора)

Согласно <https://www.moex.com/a1681>, для Derivatives Market (срочный рынок):

| Тип | Содержимое | Формат | Размер сжатого файла |
|---|---|---|---|
| **Type A — Order Log** | **все сделки и все заявки** (полный L3) | фикс. ширина | **1–3 ГБ/день** |
| **Type B — Top of the Book** | все сделки + лучшие заявки | CSV | **0.5–1 ГБ/день** |

VPIN, глубину, off-book), `Type B` — в ~3 раза дешевле по трафику, но только верх
уровня (годно для OBI/microprice по BBO, **не** годится для depth-признаков вроде
VPIN и slope-of-book).

## 5. Какие тикеры заказывать и почему

Заявка продаётся в двух вариантах: **«1 рынок»** или **«1 инструмент»** (см. 1.1).
Выбран **«1 инструмент» = CNYRUBF**: 15 000 ₽/год против 45 000 ₽/год за весь рынок.
Дополнительные тикеры при такой схеме **не бесплатны** — они требуют отдельного
заказа (1 500 ₽/мес каждый), в отличие от «1 рынок», где они идут в комплекте.
Логика набора инструментов та же (по ликвидности и уже измеренному edge):

Ликвидность (средний дневной оборот, контрактов, 2 года, из `candles`):

| Тикер | Ср. оборот/день | Макс. оборот | Дней | Приоритет |
|---|---|---|---|---|
| **CNYRUBF** | **2 669 310** | 10 324 396 | 510 | **№1 — обязательно** |
| **IMOEXF** | 811 240 | 3 965 617 | 512 | **№2** |
| **GLDRUBF** | 472 093 | 2 528 601 | 512 | **№3** |
| **USDRUBF** | 190 088 | 844 715 | 510 | **№4** |
| **EURRUBF** | 13 936 | 55 448 | 510 | **№5 — наименее полезен** |

Обоснование отбора (по уже измеренным в проекте результатам, см. `AGENTS.md`):

- **CNYRUBF** — единственный тикер со значимым OOS-edge (PF 2.15, P=0.0425),
  единственный в LIVE-allowlist. Самый ликвидный → самый информативный стакан
  (именно на нём OBI/microprice будут иметь смысл). **Заказываем в первую очередь.**
- **IMOEXF** — единственный перпетуал с `robust=true` при 100 OOS-сделках
  (P(NoEdge)=0.28 → INCONCLUSIVE). Второй по ликвидности, другой профиль волатильности.
- **GLDRUBF** — третий по ликвидности, полезен как «нетиквенный» инструмент:
  валютный фьючерс без рублёвого фактора, даёт независимый тест микроструктурных
  признаков. `lotSize=1` (важно: funding = SWAPRATE × 1, не ×1000).
- **USDRUBF** — ликвидность ниже в 3 раза, чем IMOEXF; полезен для кросс-валютной
  проверки OBI.
- **EURRUBF** — **в 190 раз** тоньше CNYRUBF (13.9 тыс. против 2.67 млн контрактов).
  Стакан почти пустой, микроструктурные признаки по нему вырождены. Имеет смысл
  только как дешёвый тариф на тики, **для L2 не приоритизировать.**

Дополнительные тикеры (только если решим перейти на тариф «1 рынок» за 45 000 ₽/год —
тогда они идут в комплекте):

- `Si` — фьючерс на доллар США, полезен для хедж-контекста (проект уже отмечал, что
  `candidateTicker == "Si"` не фильтруется в гейтах как хедж);
- `BR` — нефть, даёт товарный режим волатильности;
- `GD`/`GLDRUBTOM` — полезен для парного арбитражного анализа GLDRUBF ↔ GLDRUBTOM.

## 9. Что делаем после получения файлов

Порядок работ (запускается после того, как файлы скачаны):

1. Разложить по `data/raw/<product>/<YYYY-MM-DD>/` (оригиналы не трогаем).
2. Написать парсеры:
   - Type A / Type B — фиксированная ширина по раскладке <https://www.moex.com/a1681>;
   - реестр сделок — CSV.
3. Миграции (номера продолжают с 037) — **уже создана `038-ticks-orderbook-bbo.sql`**
   (подключена в `db.changelog-master.yaml`):
   - `ticks` — сделки: `ticker, ts, deal_id, price, volume, open_pos, direction`
     (Timescale hypertable, chunk 1 день, `UNIQUE(ticker, deal_id)`);
   - `orderbook_bbo` — секундный BBO: `ticker, ts, bid, ask, bid_size, ask_size,
     quote_count, spread_bps, obi, microprice, microprice_deviation_bps`
     (hypertable, chunk 1 день, `UNIQUE(ticker, ts)`).
   - Compression **не** применяется: нужны уникальные индексы для идемпотентной
     перезагрузки.
   - Отличие от первоначального плана: сырые `orderbook_events`/`orderbook_snapshots`
     для Типа В не нужны — MOMENT-агрегация даёт BBO напрямую, а полный depth
     возможен только из Типа А. Отдельная таблица заявок появится вместе с
     пилотом Типа А.
4. Загрузчик с `ON CONFLICT DO NOTHING` (идемпотентность повторного прогона) и
   батчами по 5 000–10 000 строк — **parser уже готов** (`MoexOrderLogParser`),
   остаются R2DBC-сущности/репозитории и сам загрузчик.
5. Слой чтения для research: эндпоинт выгрузки в CSV по тикеру/окну. **Осторожно:**
   заявленный ранее `ResearchMicrostructureController`
   (`/api/v1/research/microstructure-snapshots.csv`) в commit `3e8a8e4` фактически
   отсутствует — присутствует только persistence-слой. Endpoint надо либо дописать,
   либо читать таблицу напрямую из research-скриптов.
6. Пересчёт и проверка: OBI/microprice на истории BBO против forward-L1 (sanity check),
   затем WFA-калибровка фильтров на реальных данных.
7. Статус в `AGENTS.md` → таблица каталога аудитов.

**Оговорка:** точный объём пока неизвестен (зависит от периода в бесплатном примере
со страницы). После замера решается: грузить по дням с прогрессом и докачкой
(всегда) и достаточно ли диска.

### 9.2 Что оказалось неочевидным при реализации

Три находки, каждая из которых молча сломала бы загрузку:

1. **Агрессивные строки — не «протухшая» сторона.** Первая версия парсера
   вводила TTL для перенесённой стороны, чтобы гасить скрещённый BBO. Замеры
   это опровергли: возраст противоположной стороны при пересечении имел
   p50 = 0 мс. Скрещивание создаёт **агрессивная** строка, исполненная сразу, —
   её в стакане нет вообще. TTL не вводится.
2. **UNIQUE-ключ в гипертаблице обязан включать колонку партиционирования.**
   `UNIQUE (ticker, deal_id)` для `ticks` даёт
   `ERROR: cannot create a unique index without the column "ts"`. Ключ
   поэтому `UNIQUE (ticker, ts, deal_id)` — `deal_id` уникален и без `ts`,
   `ts` добавлен только ради требования TimescaleDB.
3. **Шаблон `EXCEPTION WHEN OTHERS + RAISE WARNING` в миграциях опасен.**
   Он есть в 012/037 и был скопирован в 038: ошибка внутри блока
   проглатывается, changeset отмечается применённым, таблиц нет — и
   падение выясняется только в рантайме. В 038 блок заменён на
   `RAISE EXCEPTION` (fail-closed). Проверено на чистом TimescaleDB
   2.17.2: `create_hypertable` для обеих таблиц проходит, повторный
   `INSERT ... ON CONFLICT` не дублирует строку.
| Отброшено агрессивных строк | 37 229 (18 960 bid + 18 269 ask) | исполнение этих заявок берётся из `ticks`, данные не теряются |
| Спред | 0.75…9.11 bps, `null` OBI/microprice = 0 | признаки вырождены на тиковых данных — это норма для L1 |
| Артефакт открытия | 2 сессии, начало отброшено (87 строк) | стартовое окно 50 мс обязательно |
| Сессии в файле | **3** (а не 17) | разрыв считать через `Duration`, не вычитанием `yyyyMMddHHmmss` как чисел |
| Границы данных | `20240930185802963 … 20241001184959230` | файл `20241001` начинается **накануне** в 18:58; дату даёт имя файла, время — MOMENT |

## 10. Проверка на бесплатном дне: есть ли вообще эффект (2026-10-02)

Замер на единственном бесплатном дне: 66 328 наблюдений стакана с разрешением
**1 мс** (состояние после каждого MOMENT), 22 859 сделок, 3 сессии.
Стенд — `MoexOrderLogMicrostructureSignalTest`.

Разрешение принципиально: MOMENT в файле Типа B — `yyyyMMddHHmmssSSS`
(миллисекунды), поэтому стакан восстанавливается с миллисекундной точностью.
На секундном агрегате (16 857 бакетов) считать OBI бессмысленно. Шаг между
наблюдениями: p50 = 70 мс, p90 = 1 293 мс.

| Горизонт | corr(OBI, fwd) | 95% CI (блочный бутстрэп) | доход «вход по знаку OBI» | 95% CI | доля угаданных направлений (базис) |
|---|---|---|---|---|---|
| 250 мс | 0,126 | [0,102; 0,151] | **0,110 bps** | [0,081; 0,140] | 53,1 % (47,2 %) |
| 1 с | 0,118 | [0,095; 0,143] | **0,128 bps** | [0,096; 0,163] | 53,0 % (47,3 %) |
| 5 с | 0,101 | [0,075; 0,129] | **0,162 bps** | [0,103; 0,216] | 53,5 % (48,2 %) |
| 30 с | 0,093 | [0,060; 0,125] | **0,319 bps** | [0,147; 0,572] | 54,0 % (48,6 %) |

`micropriceDeviationBps` ведёт себя так же (corr 0,079…0,118), но его условный
доход **идентичен** доходу OBI: знаки совпадают почти всегда. То есть это не два
признака, а один — второй переизмеряет тот же перекос стакана.

### 10.1 Контроли, без которых цифры ничего не значат

- **Placebo.** Тот же расчёт на перемешанном OBI: 0,0009…0,0059. Связь
  создаёт признак, а не устройство расчёта.
- **Контроль на импульс.** `corr(признак, прошлое)` = −0,12 на коротких
  горизонтах, поэтому корреляция с будущим могла быть лишь отражением momentum.
  Частичная корреляция, убирающая вклад прошлого движения: 0,066…0,108 —
  сигнал переживает контроль.
- **Устойчивость по половинам дня.** Знак совпадает, величины близки
  (например, 0,122 и 0,138 на 250 мс).
- **Автокорреляция.** Forward-ряды имеют лаг-1 автокорреляцию 0,91…0,99, то
  есть эффективная выборка — сотни наблюдений, а не 66 тысячи. Наивные
  p-значения по n неприменимы, поэтому доверительные интервалы считаются
  блочным бутстрэпом. Длина блока привязана к горизонту (≥5 горизонтов):
  фиксированный блок в 165 наблюдений (~11 с) на горизонте 30 с короче
  самого окна и занижает неопределённость (замеренный CI дохода 30 с
  расширяется с [0,196; 0,461] до [0,147; 0,572]).

### 10.2 Вердикт: эффект есть, но он не окупает издержки

Сигнал статистически различим и проходит все контроли. Экономически он
несостоятелен на порядок:

- доход стратегии «вход по знаку OBI» — **0,11…0,32 bps** на наблюдение;
- круговые издержки CNYRUBF: пересечение спреда (0,75…9,1 bps) +
  комиссия 1,5 ₽/контракт/сторона (≈1,1 bps на сторону при цене 13,2 ₽) +
  проскальзывание ≈1 bps, итого **3…11 bps**;
- разрыв — **в 10…100 раз**.

Отсюда решение: **на этом основании покупка пилота за 1 500 ₽/мес не
обоснована.** Замер показывает, что данные пригодны и что эффект реален, но
измеренный эффект не переживает транзакционные издержки.

Что осталось непроверенным и может изменить вывод:

- ~~**крайние значения OBI.** Эффект почти наверняка сосредоточен в хвостах
  (|OBI| > 2σ), а не в среднем по всем наблюдениям~~ — **проверено 2026-10-04,
  см. §12.1: хвост даёт 0.17…0.60 bps gross (в 2–6 раз выше среднего), но

- **другие тикеры** (Ri, Si, GLDRUBF) и режимы рынка;
- пассивная стратегия (лимитная заявка на touch) вместо кросса по mid —
  посчитана как **оптимистичная граница** (без приоритета в очереди): −2.9 bps/сделку
  в лучшей ячейке, то есть отрицательна и без учёта адверс-селекшна.

**Ограничение, которое нельзя обойти:** MOEX публикует **ровно один**
бесплатный день — `OrderLog20241001_A/B.7z` (проверено по листингу FTP,

  хвоста и в 2–6 раз выше среднего по всем наблюдениям.
- Количественно она **не окупает издержки ни в одной ячейке**: требовалось ≥ +5 bps net,
  получено ≤ −2.9 bps даже в оптимистичном passive-варианте без учёта очереди.
- Хвост **не кластеризуется** в редкие всплески (15 548 наблюдений = 4 412 эпизодов),
  то есть это «толстая середина», а не события, за которые платят как за тайну.
- Momentum-контроль на том же подмножестве даёт −0.19…+0.03 bps: импульс объясняет
  весь gross, OBI ничего не добавляет.

**Вывод:** аргумент «эффект может быть в хвостах» снят. Покупка (1 500 ₽/мес →
30 000 ₽ за 2 года) осталась бы осмысленной только ради многодневной проверки
на неделях, но и она бессмысленна при net < 0 на единственном доступном дне.

1. **Покупать ли пилот за 1 500 ₽/мес.** Ответ: **нет** — см. §12.1 и `docs/23` §7.
   Многодневная проверка бесплатно невозможна (MOEX публикует один день), forward-сбор
   Alor даёт 1 Гц L1 без истории (`docs/23`), но §12.1 закрыл гипотезу.
2. Порядок оплаты: не актуален, пока не решено «покупать ли».
3. Допустима ли лицензия, разрешающая применение результатов исследований для
   торговли (в заявке вопрос выставлен явно)? — не актуально, заявка не подаётся.
