## 4. Следующий шаг: бинарный LLM-veto на baseline CNYRUBF

Это **единственная невыполненная часть исходного плана**. Пользователь подтвердил
переход к ней после коммита.

### Почему veto, а не генерация

В `AGENTS.md` и `docs/19` зафиксировано: **LLM как источник сигнала edge не даёт**
— PF 0.71–0.81 на пяти моделях (DeepSeek, qwen3-32b, claude-opus-4.6, kimi-k3, тех-дефолт),
69 OOS-сделок, edge P=0.72–0.89. Это уже измерено и не является предметом новой задачи.
Veto — **принципиально другая гипотеза**: может ли LLM отсечь убыточные входы
из baseline-выборки, не генерируя собственных сигналов. Она **ещё не измерялась**.

### На чём измерять

**baseline CNYRUBF** — единственный измеренный конфиг с приемлемым PF:
IS PF 0.93 / 85 сделок; WFA OOS PF 0.92 / 86 OOS-сделок / consistency 0.5 (docs/19).
Калибровочный профиль: `days=730&folds=8&conf=0.60&riskPerTradePercent=30&futuresMaxContractsPerPosition=100&loadHistory=false`.

### Точки в коде (проверено сегодня)

- **Уже готовый veto-механизм: `ArbitratorAgent.adjudicate()`**
  `src/main/kotlin/com/trading/bot/agent/ArbitratorAgent.kt:79`
  - `:97-106` — `challenge.riskLevel == "CRITICAL"` ⇒ HOLD **детерминированно, до LLM**.
    Метрика `arbitrator.deterministic.override{reason="CRITICAL_CHALLENGE"}`.
  - `:108-116` — draft HOLD ⇒ HOLD; `:118-129` — `signalStrength < adaptiveConfidence` ⇒ HOLD.
  - `:183-184` — LLM недоступен ⇒ HOLD, `FALLBACK: LLM_UNAVAILABLE` (fail-closed).
  Это ближайший аналог искомого veto — **переиспользовать, не изобретать**.

- **Агенты** (`src/main/kotlin/com/trading/bot/agent/`): `TechnicalAnalysisAgent`,
  `FundamentalAnalysisAgent`, `StrategyAgent`, `ContrarianAgent`, `ArbitratorAgent`,
  `PerformanceFeedbackAgent`. Пять агентов образуют цепочку; контракт — `StrategyAction`.

- **Цепочка в бэктесте: `AgentBacktestSignalGenerator.runChain()`**
  `src/main/kotlin/com/trading/bot/backtest/AgentBacktestSignalGenerator.kt:120-206`
  - `:126-134` — `bar`, `MarketSnapshot`, окно `candles.subList(0, index + 1)`.
  - порядок: tech (`:142`) → fundamental (`:154`) → strategy draft (`:165`)
    → contrarian challenge (`:178`) → arbitrator (`:189`).
  - `:78-118` `evaluate()` — бюджет/инъекция: `withTimeout(budgetMs)`, `delay(budgetMs)`

  - **Важно:** `runChain` возвращает `decision.action` (`:205`) — это LLM-сигнал,
    а не детерминированный. Для veto нужен отдельный путь.

- **Выбор генератора: `ApiController.buildSignalGenerator()` `:169-180`**

  Вызывается на `:613`, `:992`, `:994`. `AgentBacktestSignalGenerator` в этот путь

- **Метрики бэкт��ста**: образец — `BacktestEngine.kt:553`

  `bt_llm_veto_blocked_total{ticker,reason}`.

### Ключевая проблема дизайна (продумать перед кодом)

Veto должен принимать **детерминированный** сигнал, а `runChain` генерирует
LLM-сигнал. То есть нельзя просто «включить агентов вместо детерминированных
стратегий» — это разные вещи, и первый вариант даст generation, а не veto.

Варианты (выбрать один, обосновать в `docs/20`):
- **A. Отдельный veto-путь:** детерминированный сигнал (как сейчас) + поверх
  вызов одного агента (вероятнее `ContrarianAgent`, у него уже есть
  `riskLevel`/CRITICAL-семантика) для вердикта allow/veto.
- **B. Переиспользовать `ArbitratorAgent.adjudicate`** с детерминированным
  draft'ом: подать `StrategyAgent.Draft(action=детерминированное действие,
  signalStrength=confidence)` и `ContrarianAgent.ChallengeReport` от LLM.
  Тогда veto = `riskLevel == "CRITICAL"` ⇒ HOLD, всё остальное пропуск.
  Уже реализованная fail-closed логика и метрика переиспользуются без изменений.
- **B кажется предпочтительным**: минимальный код, готовая fail-closed семантика,
  ровно та гипотеза, которую надо проверить.

**Обязательные ограничения (из `AGENTS.md`):** флаг **default off**, без
влияния на live, тесты, `test` + `integrationTest` + `ktlintCheck` зелёные.
Для research-прогона LLM обязательны `LLM_DISABLE_REASONING=true` и
`LLM_BUDGET_ENABLED=false` (иначе дефолтный лимит токенов душит параллельные вызовы);
`LLM_API_KEY` в `.env` есть.

## 5. Harness-грабли (обязательны к учёту, уже исправлены в скриптах)

1. Число сделок — поле **`totalTrades`**, а `trades` (массив) печатается как `System.Object[]`.
2. **JWT протухает** — при `401` нужен re-login c одной попыткой повтора, иначе
   падает вся серия.
3. `Start-Job` **не переживает** отдельные вызовы инструмента (каждый вызов —
   новый процесс PowerShell) ⇒ `Start-Process pwsh -File ...` + отдельный
   heartbeat (`scripts/research_hb.ps1`).
4. Spring **не импортирует `.env`** — сервер не стартует без `JWT_SECRET`;
   переменные надо выставлять в процесс **до** `Start-Process`.
5. **Дубль `maxHoldBars`** (в базовом URL и в query конфига): Spring берёт
   первое значение ⇒ max-hold молча выключается. Закреплено тестом.
6. Имя метода robustness-эндпоинта — **`backtestRobustness`**, не `robustness`
   (для рефлексии в тестах).
7. У `@RequestParam(defaultValue = "false")` атрибут `required` в аннотации
   остаётся `true` — проверять «не обязателен» можно только точечно.
8. Плейсхолдер у WFA — поле Sharpe называется **`oosSharpe`** (не `oosSharpeRatio`).
9. `ConfigCsv`: формат `Имя;Ticker;Query`, разделитель **`;`**, элемент без `;`
   молча уходил в baseline — теперь pre-flight падает.
10. Сетка SL/TP 25–600 пунктов посчитана под CNYRUBF (~90 ₽) и **ломается вне его**:
    на GLDRUBF 25 пт ≈ 0.05% (шум), на IMOEXF 600 пт ≈ 21%. Отсюда baseline GLDRUBF
    MDD 572% и 91 мин на прогон. Зафиксированы SL/TP по масштабу инструмента:
    GLDRUBF 300/600, IMOEXF 200/400, CNYRUBF 40/80.
