# 23. Прямой пилот микроструктуры (L1) — SIM, forward сбор

## 1. Цель
Проверить гипотезу: предсказательный эффект OBI/microprice сосредоточен не в среднем по всем наблюдениям, а в хвостах |OBI| > k·σ. Замер на бесплатном дне (2024-10-01, CNYRUBF) показал:
- эффект 0,11–0,32 bps (средний по всем наблюдениям)
- круговые издержки 3–11 bps (спред 0,75–9,1 bps + комиссия 1,5 ₽/контракт/сторона + проскальзывание ~1 bp)
Вывод: средний эффект не окупает издержки. Хвосты — единственное правдоподобное объяснение возможной рентабельности.

## 2. Параметры запуска (SIM)
TRADING_MODE=SIMULATION
MICROSTRUCTURE_ENABLED=true
MICROSTRUCTURE_BUCKET_MS=1000
MICROSTRUCTURE_FLUSH_INTERVAL_MS=5000
MICROSTRUCTURE_MAX_QUEUE_SIZE=20000
MICROSTRUCTURE_REST_POLLING_ENABLED=true
MICROSTRUCTURE_REST_POLL_INTERVAL_MS=1000
MICROSTRUCTURE_REST_DEPTH=1
MICROSTRUCTURE_REST_TIMEOUT_MS=5000
Retention microstructure_snapshots: 90 дней (достаточно 4 недель).
Платный L2 не используется.

### 2.1 Почему сбор идёт по REST, а не по WS (проверено 2026-10-02)
WS-подписка `QuotesSubscribe` на живом токене **не работает**: сервер отвечает
`404 "Instrument with symbol  was not found in exchange MOEX"` — символ извлекается
пустым. Проверены поля `symbol`, `security`, `secid`, `secId`, `ticker`, `code`,
`instrument`, `scode`, верхний уровень, `guids[]`, board/marketType, вложенный объект
`security`, а также команда `OrderBookGetAndSubscribe` — результат одинаковый.
Документация Alor недоступна (403), поэтому контракт не восстановлен.
Следствие: OBI/microprice по WS не вычислимы в принципе — WS-котировка не даёт
размеров стакана в используемом формате.

Рабочий путь — REST `/md/v2/orderbooks/{exchange}/{ticker}?depth=1`, который на том же
токене возвращает **цены и объёмы** (проверено вживую: CNYRUBF `12.441×564 / 12.442×570`,
SBER `273.39×4695 / 273.40×81`). Сборщик `MicrostructureRestPoller` (дефолт **off**)
складывает снимки в тот же `MicrostructureRecorder`/таблицу.

**Честное ограничение измерения.** REST-поллинг дискретен (1 Гц на тикер, последовательно
по 12 инструментам), тогда как WS-L1 даёт события на каждое изменение стакана. Поэтому:
- наблюдения — **сэмплированные во времени**, а не полный поток сделок стакана;
- признаки вида «среднее за следующие 250 мс» здесь смещены (окно наблюдения короче
  интервала опроса) — корректные горизонты для OBI начинаются от интервала опроса;
- 1 Гц достаточно для оценки формы стакана и хвостов OBI, но **не** для микроструктурного
  арбитража уровня «тик за тиком»;
- при покупке Type B/Type A полный поток вернётся через WS, и методы придётся пересчитать
  на сопоставимой частоте — сравнивать следует горизонт к горизонту, а не абсолютные bps.

Это ограничение фиксируется **до** сбора, чтобы выводы не подгонялись под инструмент.

### 2.3 Покрытие тикеров и почему нет Si/RI
Сбор идёт по 11 инструментам (CNYRUBF, CNYRUB_TOM и 9 акций), стабильно ~7.4 строки/с
(1 Гц × 11 тикеров), ошибок 0. `Si` и `RI` дают `404 No such instrument` на
`/md/v2/orderbooks/MOEX/{ticker}` — это **не дефект сбора**: это непрерывные фьючерсы,
собираемые ботом склейкой конкретных контрактов (`SiH7`, `RIZ6`, ...), и такого символа
на бирже нет. Для них нужен адресный сбор по конкретным контрактам, что за рамками пилота;
на фьючерсную сторону покрытие даёт CNYRUBF (и, при желании, перпетуалы IMOEXF/USDRUBF/
GLDRUBF/EURRUBF — у них есть реальные символы и стаканы).

### 2.4 Проверка качества признака (на старте сбора, 2026-10-02)
OBI не вырожден: диапазон [−1, 1], σ 0.47–0.70, 1200–1570 уникальных значений на тикер
при ~1800 наблюдениях. Средние спреды: CNYRUBF 0.83 bps, SBER 0.48, VTBR 2.08, LKOH 1.50 —
согласуется с измерениями бесплатного дня (0.75–9.1 bps). Признак пригоден для проверки
гипотезы хвостов; `update_count` = 1 на бакет, т.к. интервал опроса равен размеру бакета
(усреднять нечего, и это нормально для дискретного опроса).

### 2.5 Найденный при подключении баг (исправлен)
`bestSide` выбирал максимальную цену на **обеих** сторонах: лучший bid — максимум,
но лучший ask — **минимум**. При `depth=1` ошибка невидима (по одному уровню на сторону),
при глубине >1 она молча завышала бы спред и ломала microprice. Пойман регресс-тестом
`MicrostructureRestPollerParseTest` («selects best level across multiple levels»);
направление теперь передаётся явным параметром `higherIsBetter`.

## 3. Сетка проверки (фиксируется ДО сбора, без подгонки)
Пороги по σ OBI внутри дня/сессии: k = 1.5, 2.0, 2.5, 3.0
Фильтр только эта сетка. Другие параметры не подбираются.

## 4. Критерии
Критерий успеха (must-pass):
- в хвосте |OBI| >= 2.0·σ условный edge (sign-of-OBI), после вычета круговых издержек >= 5 bps/сделку
- наблюдается >= 2 последовательных торговых недели подряд
- минимальный объём сбора >= 20 торговых дней

Критерий провала (stop rule):
- за 20 полных торговых дней ни по одному порогу из сетки не достигнут критерий успеха
- и хвост даёт edge < 5 bps (с учётом издержек)
Тогда гипотеза закрывается, покупка пилота не рекомендуется.

Правило зависания (hang detection):
- нет прироста строк в microstructure_snapshots > 30 минут подряд (при рабочем времени биржи МСК) — считать процесс зависшим (опрос каждые 10 минут). Автоперезапуск не делаем, только фиксация и ожидание ручного решения.

## 5. Метрики мониторинга
- alive (actuator/health/liveness), readiness (actuator/health)
- прирост строк microstructure_snapshots (total + прирост/час)
- microstructure.flush.rows/dropped/errors/skipped
- RSS (МБ), CPU %
- ошибки БД (критичны)
- последние 40–80 строк лога
