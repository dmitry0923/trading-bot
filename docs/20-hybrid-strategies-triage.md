## 4. Что означает «100%/год» на текущем стеке

Ни одна из 10 стратегий не меняет главный вывод предыдущих прогонов:

- **live-сайзинг (maxC=1, Kelly)** на детерминированной базе даёт потолок ~1%/год;
  86 IS-сделок при maxC=1 = +0.2% за 730 дней.
- **Калибровочный риск-профиль (risk 30%, maxC 100)** даёт верхнюю оценку, но не
  edge: deployment-gate лучшей комбинации = RESEARCH_ONLY, holdout отрицательный.
- **LLM как источник сигнала** даёт PF 0.71–0.81 (DeepSeek/qwen3-32b/kimi-k3) и
  1.11 при 10 сделках (Opus) — edge нет ни на одном таймфрейме/горизонте.
- **Разнообразие инструментов** не помогает: 3 из 4 акций OOS убыточны,
  перпетуалы EURRUBF/GLDRUBF/IMOEXF убыточны, HOUR_1/DAY_1 слабее MINUTE_10.

Ограничитель — **глубина данных**: пока у Si 2.5 месяца, у VTBR 3 недели, а
BR/MX/YNDX/SBERP нет, любой прогон на этих инструментах завершается
`INCONCLUSIVE` по построению (порог 30 сделок), а не из-за качества фильтра.

Порядок увеличения полезности:

1. **Донакачка истории/инструментов** (Si, VTBR, BR, SBERP, RGBI) — снимает
   ограничитель числа сделок.
2. **Data-слой bid/ask** (сохранение стакана в БД, загрузка истории, retention) —
   открывает OBI/spread, то есть №2 и №6.
3. **Парный движок** (Z-score по спреду, dollar-neutral, P&L двух ног с funding
   по обеим) — открывает №4 и №9.
4. Только после этого — новые фильтры/LLM-арбитраж.

## 5. Реализовано: бюджет цепочки и инъекция таймаутов LLM

### 5.1 Проблема

В live бюджет LLM-цепочки был (`trading.llm-signal-budget-ms=2000`,
[LlmSignalStrategy], docs/17 §17.8 R2). В **бэктесте** его не было: таймаут LLM
приводил к тихой деградации на детерминированные fallback'и агентов
(`INSUFFICIENT_DATA`/`NEUTRAL`/`HOLD`), и отличить «LLM не ответил вовремя» от
«LLM ответил слабым текстом» по результату прогона было невозможно. Пункт
чек-листа «5% таймаутов ⇒ fail-closed HOLD, а не вход по умолчанию» был
нереализуем.

### 5.2 Конфигурация (research, оба флага **default off**)

| Флаг | Env | Default | Смысл |
|---|---|---|---|
| `bt.agent.signal-budget-ms` | `BT_AGENT_SIGNAL_BUDGET_MS` | **0** (выключен) | `withTimeout` вокруг цепочки; при превышении — fail-closed HOLD + `backtest.agent.timeout{ticker,cause=budget}` |
| `bt.agent.timeout-injection-rate` | `BT_AGENT_TIMEOUT_INJECTION_RATE` | **0.0** (выключен) | Доля сэмплов (0.0…1.0) с **реальной** задержкой `delay(budgetMs)` внутри того же `withTimeout` → тот же `TimeoutCancellationException`, что и при медленном реальном LLM. Метрика `backtest.agent.timeout{ticker,cause=injected}`. Требует `signal-budget-ms > 0`, иначе — **ошибка конфигурации**, а не молчаливый no-op |

Default 0/0.0 выбран намеренно: при нём поведение прогона совпадает с уже
измеренными LLM-WFA (DeepSeek 0.73, qwen3-32b 0.81, Opus 1.11, kimi-k3 0.71),
иначе цифры в AGENTS.md перестали бы соответствовать коду.

### 5.3 Детерминизм инъекции

`LlmTimeoutInjection` (`src/main/kotlin/com/trading/bot/backtest/LlmTimeoutInjection.kt`):
решение о таймауте — **детерминированная функция от (ticker, индекс бара)**
(FNV-1a по тикеру + splitmix-подобное перемешивание с индексом). `cycleId` в хеш
намеренно **не** входит — он меняется между прогонами.

Следствия: повторный прогон даёт ту же карту таймаутов; фолды WFA сопоставимы;
изменение `rate` двигает **порог**, а не перетасовывает выборку. Проверено
тестами: rate 0.0 → никогда, rate 1.0 → всегда, разные тикеры → разные карты,
наблюдаемая доля на 20 000 индексов ≈ заданной, монотонность по rate, ошибка вне
0.0…1.0.

### 5.4 Тесты (11 новых; всего 1599 unit + 101 integration)

- `LlmTimeoutInjectionTest` (8): границы rate, детерминизм, разные тикеры,
  монотонность, **наблюдаемая доля ≈ заданной**, ошибка вне диапазона.
- `AgentBacktestSignalGeneratorTest` (+3):
  - **`injected timeout yields fail-closed HOLD without any agent call`** —
    таймаут ⇒ HOLD и `verifyNoInteractions` всех пяти агентов (то есть **не**
    «вход по умолчанию»);
  - `chain runs normally when budget is set but injection is disabled` — бюджет
    сам по себе не меняет результат;
  - `chain is unwrapped when budget is disabled` — `budgetMs = 0` = поведение
    до изменений;
  - `injection without budget is a configuration error`.

Найденный при разработке баг: в `unitInterval` делитель был `2^SHIFT` (2^11)
вместо `2^(64-SHIFT)` (2^53) — инъекция не срабатывала ни разу. Пойман
статистическим тестом на наблюдаемую долю, а не на глаз.

### 5.5 Про задержку 1.5–3 с (look-ahead)

Отдельный механизм искусственной задержки **не реализуется сознательно**: сигнал
берётся на закрытии бара `i-1`, а исполняется на открытии `i` — для MINUTE_10
это строго консервативнее требуемых 1.5–3 с. Инъекция таймаутов моделирует не
задержку сделки, а **отказ источника сигнала**. Зафиксировано в docs/17 R6.

### 5.6 Запуск

```bash
# baseline без инъекции (совпадает с ранее измеренными прогонами)
java -jar trading-bot-2.0.0.jar --bt.agent.enabled=true --bt.agent.live-strategies=false

# тот же прогон с бюджетом 2 с (паритет с live) и 5% таймаутов
java -jar trading-bot-2.0.0.jar --bt.agent.enabled=true --bt.agent.live-strategies=false \
  --bt.agent.signal-budget-ms=2000 --bt.agent.timeout-injection-rate=0.05
```

**Блокер:** в `.env` отсутствует `LLM_API_KEY` → агенты идут по детерминированным
fallback'ам, и бюджет/инъекция ничего не измеряют. Метрики для сверки потери
сигналов: `backtest.agent.timeout{cause="injected"}` против
`backtest.agent.evaluations` и `backtest.agent.signal{action="HOLD"}`.

## 6. Четыре детерминированных ядра: реализация и измеренные вердикты (2026-09-28)

Реализовано 4 новых research-фильтра входа, **все default off**, live-путь не
затронут. Паттерн прежний: `bt.*` в `BacktestConfig` → query-override на 5
endpoint'ах (`/backtest`, `/validate`, `/robustness`, `/holdout`,
`/deployment-gate`) → `EntryFilters` в
`LiveStrategyBacktestSignalGenerator` после confidence-gate.

| Ядро | Тикер/ТФ | Фильтр | Query-параметры |
|---|---|---|---|
| S1 EMA-cross + объём | CNYRUBF M10 | EMA20>EMA50 И `Vol > SMA(Vol,20)*1.5` | `emaCross*`, `volumeSpike*` |
| S2 VWAP-отклонение в ATR | GLDRUBF M10 | `\|close−VWAP\| >= k*ATR14` (k=1.2/1.5/1.8) | `vwapMrDeviationAtr`, `vwapMrAtrPeriod` |
| S3 panic-reversal | IMOEXF H1 | RSI(14)<30 И бычий бар, **только LONG** | `panicUseSessionDrop=false` (новый флаг) |
| S4 range-squeeze + пробой объёмом | CNYRUBF M10 | `R(20) < 0.5*ATR50` сжатие, затем `Vol > SMA(Vol,20)*1.5` | `rangeSqueeze*` |

### 6.1 S1 отклонён: EMA-кросс на CNYRUBF структурно тонкий

WFA 730д, folds=8, conf 0.60, risk 30%/maxC 100: **OOS +2,34%, PF 1,77,
Sharpe 0,42 — но 3 сделки** ⇒ INCONCLUSIVE по построению (порог 30).

IS-скрининг (`/backtest`, 730д) — ни одна EMA-пара не набирает 30 входов:

| EMA-пара | Входов | PF |
|---|---|---|
| 20/50 (из ТЗ) | 5 | 0,18 |
| 10/30 | 4 | 2,92 |
| 20/100 | 2 | 0,88 |
| 9/26 | 5 | 2,77 |
| **5/20** | **12** | 0,75 |

**Объёмный фильтр не связывает:** x1.0 и x1.2 дают одинаковые 5 сделок —
убивает именно EMA-кросс, а не объём. Вывод: на CNYRUBF при conf 0.60
подтверждённых входов ~86, а EMA20/50 оставляет единицы. Дальнейшая
доводка S1 бессмысленна без смены ядра (не «порог 30 сделок», а отсутствие
событий). 27 конфигов S1 (hold × SL × TP) не гонялись: `maxHoldBars`/`wfaSlPoints`/
`wfaTpPoints` **не меняют число входов** — все 27 дали бы одну и ту же выборку
в 3 сделки.

### 6.2 Сетка SL/TP ломается вне CNYRUBF (harness-баг, исправлен)

Штатная `futuresGrid` = 25–600 пунктов посчитана под CNYRUBF (~90 ₽). Пересчёт
в % от цены:

| Инструмент | Цена | 25 пт | 600 пт |
|---|---|---|---|
| CNYRUBF | ~90 ₽ | 2,8% | 67% |
| **GLDRUBF** | ~5500 ₽ | **0,05%** (шум) | **1,1%** |
| **IMOEXF** | ~2800 | 0,9% | **21%** |

Наблюдаемое следствие: GLDRUBF baseline MDD **572%** и **91 минута** на один
прогон (in-sample перебирает всю сетку). Решение: SL/TP фиксируются **заранее**
по масштабу инструмента (без in-sample-выбора — это исключает подгонку и
ускоряет прогон ~x6): GLDRUBF SL 300/TP 600, IMOEXF SL 200/TP 400,
CNYRUBF SL 40/TP 80.

### 6.4 Найденные harness-баги (обвязка `research_wfa_four_cores.ps1`)

1. **Поле числа сделок — `totalTrades`,** а не `trades` (последнее — массив
   сделок, печатался как `System.Object[]`).
2. **JWT протухает** — 401 ронял все последующие запросы серии; добавлен
   re-login c одной попыткой повтора.
3. **`Start-Job` не переживает вызовы инструмента** (каждый вызов — новый
   процесс PowerShell) → переход на `Start-Process pwsh -File` + отдельный
   heartbeat-скрипт `research_hb.ps1`.
4. **Spring не импортирует `.env`** — сервер не стартует без
   `JWT_SECRET`; переменные надо выставлять в процесс до `Start-Process`.
5. **Дубль `maxHoldBars`** (в базовом URL и в конфиге) — Spring берёт первое
   значение, max-hold молча выключается. Закреплено тестом
   `ApiControllerEntryFilterQueryTest`.

### 7.1 S2 (VWAP-отклонение в ATR, GLDRUBF): REJECTED — спецификация противоречива

WFA 730д folds=8: `s2-mh6-atr1.2-sl300-tp600` → **0 сделок**. Диагностика
(6 зондов ADX × полоса, IS 730д) — причина не баг, а взаимоисключающие условия:

## 10. LLM-veto на baseline CNYRUBF (2026-09-29)

### 10.1 Выбор варианта: B — переиспользование `ArbitratorAgent.adjudicate`

Гипотеза, которую измеряем: **LLM, не генерируя сигналов, способен отсечь
убыточные входы из детерминированной выборки.** Это принципиально другая
гипотеза, чем уже отвергнутая генерация (PF 0,71–0,81 на пяти моделях,
docs/19 §«LLM-сигналы»). Рассматривались два варианта (docs/21 §4):

- **A** — отдельный veto-путь: детерминированный сигнал + один агент
  (вероятно `ContrarianAgent`) с вердиктом allow/veto;
- **B** — переиспользовать `ArbitratorAgent.adjudicate`, подав детерминированный
  draft (`StrategyAgent.Draft`) и LLM-вызовы контрариана/арбитра.

**Выбран B.** Обоснование:

1. **Fail-closed семантика уже реализована и покрыта тестами.** LLM недоступен /
   схема не прошла / ошибка парсинга ⇒ `HOLD` (`ArbitratorAgent.kt:183,193,205`),
   а `challenge.riskLevel == "CRITICAL"` ⇒ блок **детерминированно, до вызова
   арбитра** (`ArbitratorAgent.kt:97`, метрика
   `arbitrator.deterministic.override{reason=CRITICAL_CHALLENGE}`). Для veto это
   означает «блок», а не «пропустить сделку без оценки» — ровно то требование,
   которое проект предъявляет к LLM-пути (docs/17 §17.8 R4, R2).
2. **Не изобретается контракт вердикта:** новая схема ответа = новая валидация,
   новый парсинг, новая метрика, новая fail-closed ветка — при нулевом
   дополнительном измерении. Различие A и B — только в том, *какой* агент даёт
   вердикт; гипотеза проверяется одна и та же.
3. Логи агентов (`AgentLogRepository`) и метрики арбитра переиспользуются как
   есть, поэтому прогон даёт данные для разбора «почему заблокировано» без
   дополнительной обвязки.

Цена B — два LLM-вызова на бар-кандидат вместо одного. Это компенсировано
мемо (§10.3) и тем, что кандидатов на порядки меньше баров.

### 10.2 Семантика veto

Вход: детерминированный сигнал baseline (`bestAction`, `bestStrength`), окно
свечей и `Indicators` (уже посчитаны генератором).

- `TechnicalReport` строится **детерминированно** из `IndicatorCalculator`
  (RSI/ATR/MACD/BB/тренд) — дополнительных LLM-вызовов нет, и арбитр получает
  тот же рыночный контекст, что видит детерминированная стратегия.
- `FundamentalReport` = `NEUTRAL` с пометкой «в бэктесте фундаментальных данных
  нет». Выдумывать фундамент нельзя: варьируя его, мы бы измеряли не veto, а
  шум промпта.
- `Draft` = детерминированный сигнал: `action = bestAction`,
  `targetPrice = close` бара, `signalStrength = bestStrength`.
- Вызовы: `ContrarianAgent.challenge(...)` → `ArbitratorAgent.adjudicate(...)`.
- **Veto = `final.action == HOLD`.** Направление, цену и силу, которые вернул
  арбитр, **игнорируем** — вход остаётся детерминированным. Иначе получилось бы
  измерение генерации, которая уже отвергнута, а не veto.
- Причины блока (`bt_llm_veto_blocked_total{ticker,reason}`):
  `CHALLENGE_CRITICAL`, `ARB_HOLD`, `LLM_FAILURE`
  (`overrideReason` = `LLM_UNAVAILABLE`/`SCHEMA_REJECTED`/`PARSE_ERROR`),
  `BUDGET_TIMEOUT`, `NO_INDICATORS`, `ERROR`.
- `llmVetoBlockOnUnknown` (default `true` = fail-closed) решает судьбу **только
  отказов** LLM (`LLM_FAILURE`/`BUDGET_TIMEOUT`/`ERROR`/`NO_INDICATORS`).
  Настоящий вердикт `HOLD` блокирует вход при любом значении флага.

### 10.3 Детерминизм: два решения против «грязного» кэша

1. **Semantic cache агентов на пути veto выключена** (`bypassCache = true` в
   обоих вызовах; в `ContrarianAgent.challenge` параметр добавлен — в
   `ArbitratorAgent.adjudicate` он уже был с тем же обоснованием). Отпечаток
   семантического кэша намеренно грубый: цена до 1 знака, бакет RSI×10, знак
   MACD, а `session` берётся от `LocalTime.now()` — стенные часы, а не время
   бара. В бэктесте это даёт два искажения: вердикт одного бара применяется к
   другому (коллизии отпечатка) и прогон невоспроизводим (зависимость от
   времени суток запуска). Обход кэша здесь — условие измеримости, а не
   оптимизация скорости.
2. **Мемо вердикта по ключу `(ticker, время бара, действие)`** внутри экземпляра
   генератора. WFA заново проигрывает одни и те же бары в каждом фолде и в сетке
   подбора SL/TP (`BacktestValidator.tuneParams` → `simulateWith`), поэтому без
   мемо один вопрос уходил бы в LLM десятки раз. При `temperature = 0.0` ответ
   на идентичный вход один и тот же, поэтому мемо не искажает измерение, а
   делает его воспроизводимым и выполнимым по времени. `cycleId` в ключ не
   входит (он меняется между прогонами) — тот же приём, что в
   `LlmTimeoutInjection`.

### 10.4 Конфигурация и границы

`bt.llm-veto-*`, **default off**, live-путь не затронут (генератор существует
только в бэктесте), query-оверрайды `llmVeto*` на 5 эндпоинтах (паттерн
funding-veto/ML).

| Параметр | Default | Смысл |
|---|---|---|
| `llmVetoEnabled` | `false` | вкл. veto поверх детерминированного сигнала |
| `llmVetoBudgetMs` | `20000` | бюджет пары вызовов; превышение → fail-closed блок |
| `llmVetoBlockOnUnknown` | `true` | отказ LLM → блок (false → пропуск) |
| `llmVetoPromptVersion` | `default` | версия шаблонов промптов |
| `llmVetoSampleEvery` | `0` | 0 = veto каждого кандидата; N = каждого N-го |
| `llmVetoTemperature` | `0.0` | детерминизм |
| `llmVetoCacheNamespace` | `backtest-veto` | изоляция кэша агентов от live |

`llmVetoSampleEvery` существует из-за стоимости: 2 LLM-вызова × все

**разбавленный** veto (проверяется 1/N кандидатов) — это отдельная гипотеза со
своим размытием эффекта, её нельзя смешивать с veto на каждом кандидате.

| Прогон | OOS сделки | OOS PF | OOS Return | OOS Sharpe | Consistency | P(noEdge) |
|---|---|---|---|---|---|---|
| baseline (veto off) | 31 | 1.299 | +0.364% | 0.556 | 0.667 | 0.31 |

**Фальсификация (решающий эксперимент).** Тот же конфиг с
`llmVetoBlockOnUnknown=false` — отказы LLM пропускаются, а не блокируются —
даёт **тождественный baseline** результат (31 сделка, PF 1.2989500760596326,
consistency 0.667, до последнего знака). Значит veto-конвейер при `false`
эквивалентен детерминированной стратегии, и весь эффект `PF 1.771` дали
**исключительно отказы LLM**, срезанные fail-closed.

**Что показали логи.** За прогон арбитр вынес **40 вердиктов: 20 BUY / 20 SELL /
0 HOLD** — ни одного настоящего вето. В окне прогона зафиксировано 2 отказа
(`12:11:52`, `12:13:20`: `LLM call failed for agent=arbitrator`), ещё 1 отказ
пришёлся на 30-дневный smoke-прогон (`11:52`). **Veto Block Rate = 0/40 = 0%** —
ниже собственного порога docs/24 §4 («< 10% — LLM почти не фильтрует, veto
бесполезен»).

**Честная оговорка про арифметику (уточнено 2026-10-05 по полному логу
`build/bootrun1.log`).** Первоначальная формулировка «2 отказа объясняют падение
31 → 26» была неточной: в окне прогона (12:11–12:39) отказов арбитра **4**, а не
2 — `12:11:52`, `12:13:20`, `12:38:23`, `12:39:37` (все `TimeoutCancellationException:
Timed out waiting for 20000 ms`, то есть сетевые таймауты Router AI, не отказы
модели). Ещё один отказ `contrarian` (`12:41:06`) уже вне окна прогона; отказ
`arbitrator` в `11:52` относится к 30-дневному smoke. Итого fail-closed срезал
**4** кандидата, что согласуется с падением 31 → 26 с точностью до одной сделки,
не объяснённой логами (причина не установлена; приоритет низкий — вердикт
определяется тождественностью baseline).

**Следствие для интерпретации.** Улучшение PF 1.299 → 1.771 объясняется
исключительно **сетевыми таймаутами LLM**, случайно совпавшими с убыточными
входами. Это делает прогон fail-closed не просто неинформативным, а активно
вводящим в заблуждение: он измеряет связь «доступность LLM ↔ случайный исход
сделки», а не качество вето-сигнала. Именно поэтому метрики veto теперь
различают решения (`ARB_HOLD`, `ARB_SCORE_LOW`) и отказы (`ARB_FAILURE`,
`LLM_FAILURE`, `BUDGET_TIMEOUT`): по прогону 2026-10-05 причина «почему сделок
стало меньше» читалась только по логам, и в этом прогоне она была именно
недоступностью LLM.

**Вердикт: `REJECTED`.** По формальному критерию docs/24 §4 «PF > 1.2» прогон
его формально проходит (1.771), но критерий оказался ложноположительным на
артефакте fail-closed. Дополнительно не пройдены: `consistency` 0.500 < 0.600,
Veto Block Rate 0% < 10%, `robust=false` (26 сделок << `MIN_WALK_FORWARD_TRADES=100`),
P(noEdge) 0.13 > 0.05. Гипотеза H3 (docs/24 §8.5). `bt.llm-veto-*` остаётся `off`;
live-путь veto не имеет вовсе.

**Инфра-дефекты, найденные на этом прогоне (не связаны с логикой veto):**

1. **Параметра `agentVetoMode` в API нет.** docs/24 §3/§8 и handoff docs/21
   предписывают `?agentVetoMode=true`; фактические параметры — `llmVetoEnabled`,
   `llmVetoPromptVersion`, `llmVetoBlockOnUnknown` (таблица §10.4). Дубликат
   конфига `config/BacktestAgentConfig.kt` (реальный — `backtest/`) удалён.
2. **`/actuator/prometheus` отдаёт 500** —
   `ClassCastException: io.prometheus.metrics.model.snapshots.HistogramSnapshot$HistogramDataPointSnapshot cannot be cast to ...`
   Значит `bt_llm_veto_*` (кандидаты/блоки/allow/cache-hits) прочитать нельзя,
   и block rate взят из логов агентов. Предсуществующий баг реестра, к veto
   отношения не имеет, но метрики veto сейчас **наблюдаемы только по логам**.
3. **Баг харнесса:** скрипт по умолчанию писал baseline- и veto-прогон в один и
   тот же JSON-файл; результаты различались копированием вручную. Добавлены
   `-Out` и `-NoBlockOnUnknown`.

## 11. Риск-сетка 730д: риск не создаёт доходность (2026-09-29, `risk-grid-730d`)

**Гипотеза.** «Цель 100%/год недостижима, потому что риск мал; если поднять
`riskPerTradePercent`/`futuresMaxContractsPerPosition`, доходность вырастет».

**Метод.** WFA 730д, folds=8, conf 0.60, детерминированная стратегия CNYRUBF

смешивать выбор edge с размером позиции значило бы измерять два эффекта сразу.

1. **OOS ухудшается монотонно** с ростом риска (−2.17% → −12.38%). Ни один
   профиль не даёт плюса, не говоря о 100%/год.
2. **Число сделок одинаково (85–86) при любом риске.** Это ключевая строка
   таблицы: риск меняет только размер позиции, но не торговые решения. Значит
   на этой истории частота входов определяется confidence-gate и структурой
   сигнала, а леверидж не может добавить сделок — только умножить убыток.
3. **Deployment-gate лучшего профиля (5%/20) = `REJECTED`,
   `liveAllowed=false`**, провалено 8/8 проверок:
   `backtest` Sharpe 0.206/PF 1.036 (67 сделок) · `walk_forward` OOS PF

   `consistency` 0.375 < 0.600 · `edge_significance` P(noEdge) = 0.942 ·
   `holdout` −3.6% (17 сделок) · `holdout_sample` 17 < 30 · `robustness`
   MC p5 = −15.9%, pLoss 46.3%, stressFailed = 5.

**Итог: цель «100% в год» на текущей детерминированной стратегии признана
недостижимой.** Дальнейшее масштабирование `riskPerTradePercent`/
`futuresMaxContractsPerPosition` не рассматривается. Требуется **смена
стратегии/источника edge**, а не новый фильтр и не риск-параметр. Live-параметры
(`maxC=1`, Kelly, funding-veto off, LIVE-guard CNYRUBF) не менялись.

**Побочно найден и исправлен баг `BacktestEngine`.** На пустом фолде
`sorted.first()` бросал `NoSuchElementException`; исключение проглатывалось
общим `catch` и логировалось как «funding history unavailable». То есть
реальная ошибка маскировалась под проблему данных, а в БД при этом ряд
SWAPRATE есть и читается (тревога про funding была ложной). В старом прогоне
таких фолдов было 3 из 78 backtest-строк (`trades=0`), плюс 2 `List is empty`.
Теперь пустой срез логируется явно и не ходит в funding repository; регресс-тест
`empty candle slice does not query funding history and returns empty result`.
**Остаточный риск:** пустой срез всё ещё возвращает формальный пустой
`BacktestResult` без invalid-флага, поэтому такие фолды входят в агрегацию —
при следующем изменении движка это нужно закрыть.
